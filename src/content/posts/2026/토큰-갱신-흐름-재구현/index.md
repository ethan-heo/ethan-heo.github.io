AI와 함께 작성한 글입니다.

토큰이 만료된 순간 요청이 동시에 나가면 갱신 요청도 요청마다 따로 나간다. 2023년에 내가 만든 토큰 확인·갱신 흐름이 그랬다. 남겨 둔 기록을 바탕으로 같은 구조를 새로 재현해 이 동작을 테스트로 기록하고, 진행 중인 갱신을 공유하고 갱신을 API Route 한 곳으로 모아 고쳤다. 리프레시 토큰을 교체하는 환경에서 동시 요청 3개의 성공률은 33.3%에서 100%가 됐다.

로그인 회원이 페이지를 열어 둔 사이 액세스 토큰이 만료되면, 서비스는 리프레시 토큰으로 새 토큰을 받아 와서 하던 요청을 이어 가야 한다. 서비스는 별 문제 없이 돌아갔지만 "잘 돌아갔다"는 말에는 토큰이 만료된 그 순간에 요청이 하나만 나간다는 조건이 숨어 있었다. 이 글은 그 조건이 깨지면 무슨 일이 생기는지 테스트로 확인하고, 고칠 방향을 내가 정하고, AI가 구현한 결과를 같은 조건에서 비교한 기록이다. 기록을 바탕으로 같은 구조를 프레임워크 없는 함수로 재현했다.

## 2023년의 나는 무엇을 만들었나

토큰 만료를 확인하는 곳이 세 군데 있었다.

- **middleware**: 로그인이 필요한 경로에 들어올 때 확인한다. 새로고침처럼 서버에서 렌더링하는 경우를 맡았다.
- **`_app.getInitialProps`**: 모든 페이지에서 확인한다. `Router`로 페이지를 옮기면 클라이언트에서 렌더링하기 때문에 여기서도 확인하기로 했다.
- **요청 인터셉터**: API를 호출할 때마다 확인한다. 페이지를 옮기지 않고 머무는 동안 토큰이 만료되는 경우를 위해 나중에 추가했다.

세 곳은 같은 판정 함수를 쓴다. 판정은 단순하다. 액세스 토큰이 유효하면 그대로 쓰고, 액세스 토큰만 만료됐으면 갱신하고, 둘 다 만료됐으면 로그인 화면으로 보낸다. 인터셉터를 간단히 옮기면 이런 모습이다.

```ts
// 2023년에 만든 방식 (기록을 바탕으로 간단히 재현한 코드)
async function request(path) {
  const headers = {};

  if (isLogined()) {
    // 요청마다 토큰을 확인하고, 만료됐으면 갱신한다
    const { isRenew, token, refreshToken } = await checkToken(cookies, refresh);

    if (isRenew) {
      cookies.set("token", token);
      cookies.set("refreshToken", refreshToken);
    }
    headers.Authorization = token;
  }

  return send({ path, headers });
}
```

요청이 하나일 때는 아무 문제가 없다. 문제는 이 함수에 "지금 갱신이 진행 중인지"를 아는 장치가 없다는 점이다.

## 재현해 보니 드러난 빈틈

남아 있는 기록을 바탕으로 AI와 함께 이 구조를 재현하고(Node 함수, 가짜 시계, 가짜 인증 서버), 요청을 동시에 보내 보았다. 확인한 빈틈은 네 가지다.

1. **동시 요청마다 갱신이 따로 나간다.** 액세스 토큰이 만료된 상태에서 API 3개를 동시에 호출하면 갱신 요청도 3번 나간다. 10개면 10번이다.
2. **백엔드가 리프레시 토큰을 교체하면 요청이 실패한다.** 갱신할 때마다 리프레시 토큰을 새로 발급하고 이전 것을 무효로 만드는 백엔드라면, 먼저 끝난 갱신이 나머지 갱신의 토큰을 무효로 만든다. 3개를 동시에 보내면 결과가 `fulfilled, rejected, rejected`다.
3. **새로고침 한 번에 갱신이 두 번 나간다.** middleware가 갱신한 토큰은 응답 쿠키에만 실린다. 같은 요청에서 뒤따라 실행되는 `getInitialProps`는 요청 쿠키의 옛 토큰을 읽으므로 한 번 더 갱신한다.
4. **쿠키 삭제가 버려지는 응답에 적용된다.** middleware에서 `NextResponse.next().cookies.delete(...)`를 호출하는데, 이 호출은 새 응답 객체를 만들어 쿠키를 지우고 그 객체를 버린다. 실제 응답에는 반영되지 않는다.

2번은 실제 백엔드가 그렇게 동작하는지 기록으로 알 수 없었다. 응답에 새 `refreshToken`이 들어 있고 프론트엔드가 그 값으로 쿠키를 바꾼다는 것만 남아 있었다. 그래서 재현에서는 교체 여부를 설정값으로 두고 두 경우를 모두 테스트했다.

이 빈틈 때문에 실제 서비스에서 오류가 났는지는 기록으로도 기억으로도 확인하지 못했다. 이번에 찾은 것은 "동시에 요청이 나가는 순간에 대한 동작을 코드가 정하지 않았다"는 사실이다.

## 테스트로 먼저 기록했다

고치기 전에 빈틈을 테스트로 남겼다. 당시 방식이 요구사항을 어기는 사례는 `it.fails`로 썼다. `it.fails`는 기대값이 틀릴 때 통과한다. 통과한다는 것은 당시 방식이 그 사례에서 틀리다는 뜻이다. 개선안이 고치면 같은 기대값을 일반 `it`으로 옮겨 검증한다.

```ts
// 당시 방식은 이 기대값을 만족하지 못하므로 it.fails로 기록한다
it.fails("갱신을 한 번만 요청한다", async () => {
  await Promise.all([api.request("/a"), api.request("/b"), api.request("/c")]);
  expect(server.refreshCallCount).toBe(1);
});
```

`it.fails`는 어떤 이유로든 실패하면 통과한다. 오타로 실패해도 통과한다. 그래서 5개를 일반 `it`으로 바꿔 실행하고 실패 메시지가 의도한 이유인지 확인했다. `expected 3 to be 1`(갱신이 3번 나갔다), `['fulfilled','rejected','rejected']`, `expected 2 to be 1`(새로고침의 이중 갱신)처럼 모두 단언 실패였다.

기대값이 아직 정해지지 않은 동작(갱신이 실패했을 때 세 곳이 서로 다르게 반응하는 것 등)은 `it.fails`로 틀렸다고 표시하지 않았다. 지금 동작만 통과하는 테스트로 기록하고, 기대값은 개선안을 정할 때 확정했다. 테스트는 22개(일반 17, `it.fails` 5)다.

## 고치는 방향은 내가 정했다

AI가 방향 후보를 정리했고, 어느 쪽으로 갈지는 내가 정했다. 선택한 이유는 내 말로 남겼다.

- **동시 갱신은 진행 중인 갱신을 공유한다.** 이유는 API 요청 때 토큰 확인을 한 번만 하게 하려는 것이다. `Promise`로 여러 요청을 pending 상태로 두고, resolve로 여러 요청의 상태를 한꺼번에 바꿀 수 있어서 적절한 조치라고 생각했다. 후보는 요청을 한 줄로 세워 순서대로 처리하는 방식도 있었다.
- **갱신은 API Route에서 한다.** middleware는 모든 요청이 거치는 단계라 처리 속도가 중요하다고 판단했다. middleware와 `getInitialProps`는 만료 여부만 확인한다. 액세스 토큰만 만료됐으면 갱신 API Route로 보내고, 갱신된 쿠키를 응답에 담아 원래 경로로 되돌린다. 후보는 갱신한 토큰을 같은 요청 안의 뒤쪽 확인이 읽게 하는 방식이었다.
- **두 토큰이 모두 만료되면 요청을 보내지 않고 거절한다.** 두 토큰이 모두 만료됐으므로 요청을 거부하는 것이 맞다고 생각했다. 후속 처리는 호출한 쪽이 예외 처리로 한다. 당시에는 만료된 토큰을 그대로 실어 보냈다.

로그인이 필요 없는 경로에 만료된 쿠키가 남는 동작은 이번 범위에서 뺐다. 기록으로는 원본에서도 같은 현상이 있었는지 확인할 수 없기 때문이다.

## AI가 구현하고, 같은 조건으로 비교했다

구현과 측정은 AI에게 맡겼다. 나는 테스트 결과와 수치를 확인했다. 핵심은 진행 중인 갱신을 공유하는 부분이다.

```ts
// 개선 코드 (간단히 옮긴 코드)
function createRefreshCoordinator(refresh) {
  let inFlight;

  return (refreshToken) => {
    if (!inFlight) {
      const current = refresh(refreshToken).finally(() => {
        // 성공이든 실패든 끝나면 비워서, 다음 만료 때 새로 갱신할 수 있게 한다
        if (inFlight === current) inFlight = undefined;
      });
      inFlight = current;
    }
    return inFlight;
  };
}
```

먼저 도착한 요청이 갱신을 시작하면, 나머지는 같은 `Promise`를 기다렸다가 같은 결과를 쓴다. 갱신이 실패하면 기다리던 요청이 모두 같은 오류로 거절되고, 다음 요청은 다시 갱신할 수 있다.

테스트는 32개를 더했다. `it.fails` 5개와 같은 기대값을 일반 `it`으로 통과시켰고, 전체 54개가 모두 통과한다. 테스트가 정말 결함을 잡는지 알려고 개선 코드를 일부러 망가뜨려 보기도 했다. 갱신 공유를 없애면 관련 테스트 5개가, 실패 뒤 초기화를 없애면 1개가, `myInfoSession` 삭제를 없애면 1개가 실패했다.

같은 조건(가짜 시계, 가짜 서버, 동시 요청 3개와 10개, 왕복 지연 50ms)으로 당시 방식과 개선 방식을 나란히 쟀다.

| 상황 | 당시 방식 | 개선 방식 |
|---|---|---|
| 동시 요청 3개 / 10개의 갱신 횟수 | 3번 / 10번 | 1번 / 1번 |
| 리프레시 토큰을 교체할 때 동시 요청 3개 / 10개의 성공률 | 33.3% / 10.0% | 100% / 100% |
| 새로고침 한 번의 갱신 횟수 | 2번 | 1번 |
| 동시 요청 완료 시간 (중앙값) | 약 106~108ms | 약 108~109ms |

## 결과를 어떻게 읽었나

갱신 횟수가 3번에서 1번으로 줄었는데 완료 시간은 그대로다. 당시 방식도 갱신 3개를 병렬로 보내기 때문에 시간이 더해지지 않는다. 가짜 서버에서 갱신 한 번은 50ms로 고정이므로, 직렬이었다면 갱신만 150ms가 걸렸을 것이다. 같은 당시 방식을 두 번 쟀을 때 중앙값이 106.4ms와 108.5ms로 달랐고, 이 차이가 타이머 오차다.

그래서 이 개선은 성능 개선이 아니라 **정확성 개선**이다. 핵심은 토큰을 교체하는 백엔드에서 동시 요청의 성공률이 33.3%에서 100%가 된 것이다. 불필요한 갱신이 사라진 것은 서버가 받는 요청이 줄어든 부수 효과다. 속도가 빨라졌다고 쓰지 않는다.

## 느낀 점

- **AI가 한 일**: 기록을 바탕으로 당시 구조를 재현하고, 테스트와 `it.fails`를 만들고, 정한 조건대로 측정하고, 내가 고른 방향대로 구현했다.
- **내가 한 일**: 어떤 상황에서 누가 쓰는지 정하고, 테스트가 내 의도를 담았는지 확인하고, 방향과 이유를 정하고, 수치를 해석했다.

AI는 동시에 요청이 나가는 상황을 빠르게 재현해 주었다. 그 결과를 보고 "무엇을 고칠 것인가"와 "왜 그렇게 고치는가"를 정하는 일은 내 몫이었다.

## 한계

- **재현의 범위**: 남겨 둔 기록을 바탕으로 재현했다. 기록에 없는 세부 동작은 당시와 다를 수 있다.
- **갱신 실패 처리**: 갱신이 실패하면 토큰 쿠키를 지우고 로그인 페이지로 redirect한다. 일시적인 네트워크 오류도 같게 처리하므로 로그아웃이 되고, 재시도는 하지 않는다.
- **redirect 비용**: 갱신을 API Route로 옮기면 새로고침 때 redirect를 한 번 더 거친다. 이 비용은 측정하지 않았다. "middleware의 처리 속도가 중요하다"는 선택 이유와 직접 이어지는 값이라 따로 재야 한다.
- **측정 환경**: 가짜 서버와 가짜 시계로 잰 값이다. 실제 네트워크 지연과 서버 부하는 반영하지 않았다.
- **재현 범위 밖**: 서명 검증, 401 응답을 받아 갱신하는 경로, 만료 표시를 받은 `_app`이 화면에서 하는 일은 다루지 않았다. 만료 판정이 클라이언트 시계에 의존하는 점도 그대로다.
- **실제 백엔드**: 리프레시 토큰을 교체하는지 알지 못해서 두 경우를 모두 테스트했다. 교체하지 않는 백엔드라면 이번 개선의 효과는 불필요한 요청이 줄어드는 정도다.
