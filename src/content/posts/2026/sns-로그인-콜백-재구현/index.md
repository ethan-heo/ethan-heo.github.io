AI와 함께 작성한 글입니다.

2022년에 내가 만든 SNS 로그인 콜백에는 인가 요청의 `state`가 없었고, 로그인 결과 이동에는 301을 썼다. 기록을 바탕으로 같은 흐름을 가짜 제공자와 가짜 서비스 서버로 재현해 보니, `state`가 없으면 로그인을 시작하지 않은 브라우저도 공격자 계정으로 로그인됐고 301은 로그인 결과 이동에 맞지 않는 설정이었다. 이런 문제 여섯 가지를 `it.fails` 11개를 포함한 테스트 48개로 남겼다.

SNS 로그인은 제공자 화면에서 인증을 마치면 서비스의 콜백 주소로 돌아오는 흐름이다. 2022년 7~8월에 내가 이 콜백을 만들었다(네이버와 페이스북). 로그인에 성공하면 보던 페이지로, 가입하지 않았다면 회원가입으로 보내는 일이었고, 서비스는 별 문제 없이 돌아갔다.

이번에 기록을 다시 보니 `state`와 301은 둘 다 내가 몰랐던 것이었다. AI와 질의응답을 하며 그렇게 한 이유를 되짚어 보았는데, 답은 둘 다 "몰랐다"였다.

이 글은 남아 있는 기록을 바탕으로 콜백 흐름을 프레임워크 없는 함수로 다시 만들고, 그 문제를 테스트로 남긴 기록이다. 회사 코드는 쓰지 않았고, 제공자와 서비스 서버는 가짜로 만들었다. 이 글에서는 코드를 고치지 않았고 성능도 재지 않았다. 문제를 눈에 보이게 만드는 데까지가 범위다.

## 2022년의 나는 무엇을 만들었나

콜백의 흐름은 다섯 단계다.

1. 로그인 버튼이 제공자의 인가 URL로 이동한다. 이 요청에 `state`는 없다.
2. 제공자가 인가 코드(`code`)를 붙여 콜백 경로로 돌려보내고, 서비스가 이를 받는다.
3. `code`로 제공자 토큰을 받고 사용자 정보를 조회한다. 이메일 형식이 아니면 오류로 처리한다.
4. 서비스 로그인 API에 이메일과 SNS 사용자 ID를 보낸다. 응답이 200이 아니면 가입하지 않은 사용자로 보고 회원가입으로 보낸다.
5. 성공하면 로그인 전에 보던 페이지가 있을 때 그곳으로, 없으면 홈으로 보낸다. 실패하면 오류 코드를 쿠키에 담아 로그인 화면으로 보낸다.

이메일과 SNS 사용자 ID만 보내는 방식은 제공자의 사용자 정보 응답을 확인한 뒤 백엔드 개발자와 논의해 정했다.

내가 쓴 범위는 2022년의 원래 로직까지다. 콜백을 Next.js 13의 `middleware.ts`로 옮긴 일과 카카오 로그인은 이후 다른 팀원이 했다. 재현은 지금의 구조(middleware 한 곳에서 네이버·카카오 두 제공자를 처리)를 따랐기 때문에, 내가 쓴 부분과 이후에 바뀐 부분이 섞여 있다.

## 재현해 보니 보인 것

재현한 코드로 시나리오 7개를 직접 돌려 보았다. 보던 페이지로 돌아가는 정상 흐름, 홈으로 가는 흐름, 가입하지 않은 사용자, 두 가지 오류, 그리고 아래 1번과 3번 상황이다. 이 과정에서 확인한 문제는 여섯 가지다.

1. **`state`가 없어서 다른 사람의 로그인을 내 브라우저에 끌어올 수 있다.** 공격자가 자기 계정으로 SNS 로그인을 시작해 받은 콜백 주소를 피해자가 열게 하면, 서비스는 그 `code`를 그대로 받아 피해자의 브라우저를 공격자 계정으로 로그인시킨다. 피해자가 이후 입력하는 주문·배송지 같은 정보가 공격자 계정에 쌓일 수 있다. 재현에서는 로그인을 시작하지 않은 브라우저가 공격자 계정의 콜백 주소를 열자 그 브라우저에 공격자 계정의 로그인 토큰이 저장됐다.
2. **콜백의 모든 이동이 301이다.** 301은 영구 이동이라 브라우저가 결과를 캐시해도 된다는 뜻이다. 로그인 결과는 매번 달라지므로 302·303·307이 맞다.
3. **로그인 뒤 돌아갈 주소를 검증하지 않는다.** 이 주소를 쿠키에 담아 두는데, 값이 `@other.test/landing`으로 시작하면 이동 주소가 `https://app.example.test@other.test/landing`이 된다. URL에서 `@` 앞은 사용자 정보로 해석되므로 실제 호스트는 `other.test`다. 다만 이 쿠키를 심으려면 같은 사이트에서 쿠키를 쓸 수 있어야 하므로, 위험은 그 한도 안에서만 성립한다.
4. **서비스 로그인 API가 200이 아니면 무엇이든 미가입으로 본다.** 회원이 없다는 뜻의 404는 회원가입으로 보내는 것이 맞다. 하지만 서버 오류인 500도 회원가입으로 간다.
5. **제공자 응답의 상태 코드를 확인하지 않는다.** 제공자가 오류를 보내도 응답을 그대로 읽고 다음 단계로 넘어간다. 토큰 요청이 500이어도 그다음 사용자 정보 요청이 나간다.
6. **이메일 검사가 느슨하고, 오류 원인이 드러나지 않는다.** 이메일 형식 오류도 인가 코드가 없는 경우와 같은 일반 실패 코드로 처리된다. 이메일 검사도 느슨해서 도메인에 점이 없는 `user@example`이 통과한다.

## 테스트로 먼저 기록했다

고치기 전에 당시 동작과 문제를 테스트로 남겼다. 지금 동작이 요구사항대로인 것은 일반 `it`으로, 기대값이 분명한데 당시 방식이 어기는 것은 `it.fails`로 썼다. `it.fails`는 기대값이 틀릴 때 통과한다. 통과한다는 것은 당시 방식이 그 사례에서 틀린다는 뜻이고, 나중에 고치면 같은 기대값을 일반 `it`으로 옮긴다.

```ts
// 당시 방식은 이 기대값을 만족하지 못하므로 it.fails로 기록한다
it.fails("콜백의 성공·미가입·오류 이동이 301이 아니다", async () => {
  const response = await callback({ code: "valid-code" });
  expect(response.status).not.toBe(301);
});
```

테스트는 48개다. 정상 흐름 19개, 오류 처리 9개, 이메일 경계값 9개가 일반 `it`이고, 위 여섯 가지 문제를 기대값 8개로 나눠 `it.fails` 11개로 썼다. 같은 기대값을 두 제공자와 응답 종류별로 나눠 적어서 8개가 11개가 됐다.

모든 비정상을 문제로 적지는 않았다. 서비스 로그인 API의 404는 회원가입으로 가는 것이 맞아서 일반 테스트로 당시 동작을 고정했고, 500만 `it.fails`로 두었다.

`it.fails`는 오타로 실패해도 통과한다. 그래서 11개를 일반 `it`으로 바꿔 실행하고 실패 이유를 하나씩 봤다. `state` 없음은 `false`, 공격자 계정의 토큰 저장은 `service-access-3`이 저장된 값, 301은 상태 코드 `301`, 제공자 오류 뒤에도 사용자 정보 요청이 나간 것은 `Array(1)`, 호스트는 `other.test`, `user@example`은 이메일로 통과, 오류 코드는 기대한 `EMAIL_FORMAT`이 아니라 `AUTH_FAILED`였다. 모두 의도한 이유의 단언 실패였다. 테스트가 처음부터 전부 통과해서 오히려 의심스러웠기 때문에 이 확인을 했다.

## 내가 몰랐던 것

AI와 질의응답에서 301을 쓴 이유를 물었을 때는 "리다이렉트 상태 코드의 차이를 잘 알지 못했다"고 답했고, `state`를 쓰지 않은 이유는 "몰랐다"고 답했다. 기억을 더듬어 만든 이유가 아니라 실제로 몰랐던 것이다.

`state`는 이번에 처음 제대로 접했다. 로그인을 시작하지 않은 브라우저가 공격자 계정으로 로그인되는 것을 재현에서 직접 보고 나서야 이 값이 무엇을 막는지 이해했다. 방식은 이렇다. 로그인을 시작할 때 랜덤값을 만들어 쿠키에 저장하고 같은 값을 인가 URL 쿼리에 붙인다. 제공자가 이 값을 콜백에 그대로 돌려주면, 쿠키의 값과 비교해 이 브라우저가 시작한 로그인인지 확인한다.

301은 장애를 일으킨 버그가 아니라 의미가 맞지 않는 설정이었다. 브라우저 캐시는 요청 URL을 기준으로 하는데, 콜백 URL에는 로그인마다 달라지는 `code`가 붙어서 같은 URL이 반복되기 어렵다. 콜백 이동이 캐시되어 생긴 문제는 없었다는 기억과 맞는다.

## 고친다면

이 글에서는 구현하지 않았다. 고친다면 아래 두 가지부터 바꾸겠다. 위에서 쓴 `it.fails`는 고친 뒤 통과해야 하는 기준이 되고, 그때 일반 `it`으로 옮긴다.

- **`state`**: 인가 URL을 만드는 곳에서 랜덤값을 만들어 쿠키에 저장하고 URL에 붙이고, 콜백에서 쿠키 값과 비교한다.
- **응답 코드**: 콜백의 이동을 302·303·307 중 하나로 바꾼다.

## 느낀 점

- **AI가 한 일**: 기록을 바탕으로 콜백 구조를 재현하고, 테스트와 `it.fails`를 만들고, `it.fails`를 일반 `it`으로 바꿔 실패 이유를 확인했다.
- **내가 한 일**: 사용 시나리오(보던 페이지로 돌아가는 로그인)와 제공자 범위(네이버·카카오)를 정하고, 재현 요구사항을 확정하고, 재현한 코드를 읽고 데모를 직접 돌려 보고, 테스트가 의도한 이유로 통과하는지 점검 질문에 답했다.

잘 돌아가는 코드와 맞는 코드는 다르다는 점을 확인했다. `state`가 없어도 301이어도 정상 로그인은 모두 성공한다. 문제는 "로그인을 시작하지 않은 브라우저"처럼 정상 사용에서는 만들어지지 않는 상황을 일부러 만들어야 보였다.

## 한계

- **재현의 범위**: 남겨 둔 기록을 바탕으로 재현했다. 기록에 없는 세부 동작은 당시와 다를 수 있다. 제공자별로 따로 있던 콜백 코드를 어댑터 두 개와 공통 처리로 합쳤으므로 호출 순서와 응답은 같아도 코드 모양은 다르다.
- **내 코드와 이후 코드의 혼재**: 재현한 구조에는 이후 팀원이 추가한 카카오 로그인과 middleware 이전이 포함되어 있다.
- **가정**: 쿠키 값이 `undefined`일 때 빈 문자열로 직렬화된다고 가정했다. 가짜 브라우저는 이동을 따라가지 않고 301 캐시도 흉내 내지 않아서, 301은 응답 코드로만 확인했다.
- **가짜 서버**: 제공자와 서비스 로그인 API는 가짜다. 실제 제공자 응답과 다를 수 있다.
- **토큰 판정**: 로그인 필요 페이지의 토큰 판정은 별도 항목(07)의 일이라, 토큰 쿠키가 있으면 통과시키는 것으로 단순화했다.
- **고치지 않았고 측정하지 않았다**: 개선 구현과 성능 비교는 이번 범위에 없다.
- **실제 영향**: 당시 `state` 부재로 실제 피해가 있었는지는 기록으로 확인할 수 없다.
