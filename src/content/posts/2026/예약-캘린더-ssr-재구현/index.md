AI와 함께 작성한 글입니다.

월 캘린더는 날짜마다 예약 4건만 그리는데, 서버는 한 달 치 예약 전체를 받아 처리하고 있었다. 2023년에 내가 만든 예약 캘린더 SSR이 그랬다. 기록을 바탕으로 같은 구조를 재현해 서버 CPU 시간을 항목별로 쪼개 보니, 대부분이 화면에 그리지 않는 예약을 파싱·정규화·직렬화하는 일이었고 병목은 메모리가 아니라 CPU였다. 초기 화면에 필요한 예약만 받도록 고치자 월 예약 8,000건 기준으로 props가 9,886.9KB에서 90.4KB로, SSR 1건의 서버 CPU 시간이 약 51ms에서 약 1.3ms로 줄었다. 8,000건은 기억에 의한 추정이고, 수치는 가짜 API 서버로 재현한 환경에서 잰 값이다. 요약을 만드는 비용은 API 서버로 옮겨 갔고 이번에는 재지 않았다.

예약 관리 서비스의 월 캘린더는 한 달 치 예약을 서버에서 받아 첫 화면을 그린다. 2023년에 내가 이 초기 화면을 서버 사이드 렌더링(SSR)으로 옮겼다. 클라이언트에서 조회하던 때는 로딩 화면이 보이는 것이 문제였고, 레거시 서비스와 같은 UX를 내려면 로딩 없이 첫 화면이 그려져야 했기 때문이다.

그 뒤 예약이 몰리는 시간대에 Next.js 서버의 CPU 사용량이 급증하고 서버가 멈춘 적이 있다. 재시작으로 복구했다. 응답 하나에 화면에 쓰지 않는 데이터가 대부분이라는 점이 원인에 포함된다고 보았다. 백엔드 개발자가 초기 화면용 API와 상세 API를 나누자는 의견을 주었고 적용을 논의했지만, 더 급한 일정이 생겨 진행하지 못했다.

이 글은 그 흐름을 남아 있는 기록을 바탕으로 프레임워크 없는 함수로 다시 만들고, 무엇이 서버 CPU를 쓰는지 재 본 뒤, 고치는 방향을 정해 같은 조건에서 비교한 기록이다. 회사 코드는 쓰지 않았고, 가짜 데이터와 가짜 API 서버로 구성했다.

## 2023년의 나는 무엇을 만들었나

월 보기 SSR의 요청 흐름은 세 단계였다.

1. **공통 요청 6개**: 토큰 발급, 내 정보, 공통 메뉴, 매장 정보 같은 요청을 차례로 보낸다.
2. **기준 요청 4개**: 직원, 영업시간 같은 기준 데이터를 `Promise.all`로 보낸다.
3. **기간 요청 5개**: 예약, 예약 막기, 휴일 같은 기간 데이터를 `Promise.all`로 보낸다.

운영 환경에서는 SSR 한 번에 REST API로 요청이 15개 나간다. 이 가운데 예약 요청이 문제의 중심이다. 월 보기는 그 달 1일이 속한 주의 일요일부터 42일(6주)을 조회하는데, 예약은 페이지를 나누지 않고 기간 전체를 한 번에 받는다. 그런데 화면은 날짜마다 예약 4건만 그리고 나머지는 `+N개 더보기`로 접어 둔다.

```ts
// 2023년에 만든 방식 (기록을 바탕으로 간단히 재현한 코드)
export async function getServerSideProps(context) {
  const common = await fetchCommonInOrder();          // 6개, 앞 요청이 끝나야 다음을 보낸다
  const base = await Promise.all(fetchBaseData());     // 4개
  const [bookings, ...others] = await Promise.all([    // 5개
    api.findBookings({ isPaged: false, start, end }),  // 42일 치 예약 전체
    ...fetchPeriodData(),
  ]);

  // 서버에서 정규화한 결과가 props로 직렬화된다
  return { props: { ...normalize(bookings, others), base, common } };
}
```

정규화 단계에서 예약 한 건마다 캘린더 이벤트와 리소스를 하나씩 만들고, 둘 다 예약 객체 전체를 담았다. 이 선택이 아래에서 문제가 된다.

## 재현해 보니 보인 것

월 예약 8,000건 매장을 기준으로 재현했다. 8,000건은 기록으로 확인한 값이 아니라 내 기억에 의한 추정이어서, 테스트 데이터의 크기로만 썼다. 2,000건과 100건도 같이 재서 크기에 따른 차이를 보았다.

- **받는 예약은 8,000건인데 그리는 예약은 124건이다.** 예약이 있는 31일에 날짜마다 4건씩이므로 1.6%다.
- **응답 합계는 3,972.9KB인데 props는 9,886.9KB다.** 예약 한 건이 이벤트와 리소스에 한 번씩 실려서 약 2.5배가 된다. 메모리에서는 두 객체가 같은 예약을 가리키지만, props는 JSON 문자열로 직렬화되므로 참조가 사라지고 내용이 두 번 적힌다.
- **보기를 바꾸면 요청 5개를 전부 다시 보낸다.** 월 보기에서 이미 받은 날짜가 주 보기 범위에 들어 있어도 재사용하지 않는다. 이것이 당시에 문제였는지는 기록으로도 기억으로도 확인하지 못했다.
- **날짜 쿠키를 검증하지 않는다.** 첫 화면의 날짜를 쿠키로 받는데, `abc`를 넣으면 SSR이 `Invalid time value`로 중단되고, `2026-13-45`를 넣으면 날짜가 넘쳐서 2026-12-27~2027-02-06을 조회한다. 오류도 나지 않는다.

## 테스트로 먼저 기록했다

고치기 전에 당시 동작과 빈틈을 테스트로 남겼다. 요구사항을 지키는 동작은 일반 `it`으로, 기대값이 분명한데 당시 방식이 어기는 사례는 `it.fails`로 썼다. `it.fails`는 기대값이 틀릴 때 통과하므로, 통과한다는 것은 당시 방식이 그 사례에서 틀린다는 뜻이다.

```ts
// 당시 방식은 이 기대값을 만족하지 못하므로 it.fails로 기록한다
it.fails("props에 같은 예약이 한 번만 실린다", async () => {
  const props = await getServerSideProps(context);
  expect(countOccurrences(JSON.stringify(props), "booking-1")).toBe(1);
});
```

`it.fails`는 오타로 실패해도 통과한다. 그래서 3개를 일반 `it`으로 바꿔 실행하고 의도한 이유로 실패하는지 확인했다. 쿠키 `abc`는 `Invalid time value`로 중단됐고, `2026-13-45`는 오류 없이 엉뚱한 기간을 조회했고, props 이중 적재는 `expected 2 to be 1`이었다.

보기 전환 때의 재조회는 기대값을 정할 근거가 없어서 `it.fails`로 틀렸다고 표시하지 않고, 지금 동작만 통과하는 테스트로 기록했다. 테스트는 41개(일반 38, `it.fails` 3)다.

## 무엇을 재야 하는지 정했다

처음에는 메모리 사용량이 문제일 것이라고 보았다. 예약이 props에 두 번 실리면 불필요한 메모리가 든다고 생각했기 때문이다. 그래서 지표를 이렇게 정했다.

- 주 지표: SSR 응답 시간, props 크기, SSR 1건당 서버 메모리
- 보조 지표: 동시 요청 시의 메모리 최댓값
- 조건: 월 8,000건(비교용 2,000건·100건), 요청당 API 지연 20ms, 서버는 vCPU 2개·메모리 1GiB 사양을 가정하고 힙 한도를 1GB로 고정했다.

첫 측정에는 오류가 있었다. 가짜 API 서버가 요청마다 예약 8,000건을 만들고 직렬화하는 시간(약 39ms)까지 SSR의 CPU 시간으로 세었고, 반대로 Next가 실제로 하는 props 직렬화는 빠져 있었다. 가짜 서버의 응답을 한 번만 만들어 캐시하고 props 직렬화를 측정에 포함시킨 뒤 다시 쟀다. 그 결과가 아래의 기준 성능이다.

| 항목 | 값 |
|---|---|
| SSR 1건 서버 CPU | 약 51ms |
| props `JSON.stringify` | 약 21ms (42%) |
| 응답 `JSON.parse` | 약 14ms (27%) |
| 정규화 | 약 7ms (14%) |
| 한 프로세스의 처리 한계 | 초당 약 19.7건 |

서버 CPU의 대부분을 쓰는 곳은 예약 파싱, 정규화, props 직렬화다. 모두 **화면에 그리지 않는 예약 7,800여 건을 다루는 일**이다.

예상과 달리 병목은 메모리가 아니라 CPU였다. 대형 매장의 요청이 한꺼번에 들어오는 경우를 따로 재 보니(요청이 몰리는 상황은 내가 추가로 요청했다), 동시 요청이 100건이면 마지막 응답이 약 4.4초, 600건이면 약 25초 뒤에 나갔다. 한 프로세스가 요청을 차례로 처리하는데 초당 20건을 넘는 요청이 계속 들어오면 줄이 계속 길어진다. 메모리는 동시 요청 수와 상관없이 힙 증가가 60~95MB 수준에서 멈췄다. 한 번에 하나씩 끝나고 해제되기 때문이다.

2023년 운영 장애에서 CPU가 급증해 높게 유지되다가 서버가 멈춘 모습과 이 결과의 모양이 같다. 다만 이 재현만으로 장애 원인을 확정할 수는 없다. 종료 원인(메모리 부족인지 헬스 체크 실패인지)과 요청 시간 분포는 확인하지 못했다.

## 고치는 방향은 내가 정했다

AI가 개선 후보를 정리했고, 어느 쪽으로 갈지는 내가 정했다. 고른 것은 **초기 화면에 그려지는 예약만 받는 방식(B)**이다.

B를 고른 이유는 2023년에 못 한 일을 이어 가고 싶어서다. 당시 백엔드 개발자가 초기 화면용 API와 상세 API를 나누자는 의견을 주었고, 그 의견을 적용하려고 논의하던 중 더 급한 일정이 생겨 진행하지 못했다. 그 아이디어가 이번 재현에서 정말 서버 비용을 줄이는지 직접 확인해 보고 싶어서 개선 방향으로 잡았다.

정한 범위는 다음과 같다.

- **월 보기만 바꾼다.** 주·일 보기는 시간표에 예약을 모두 그려야 하므로 지금 방식을 유지한다.
- **API는 가정한다.** 날짜별 예약 건수와 날짜당 앞 4건만 주는 요약 API, 날짜 하나의 전체 예약을 주는 상세 API가 있다고 가정했다. 실제 백엔드를 바꾼 것이 아니라 실험을 위한 가정이다.
- **`+N개 더보기`를 누르면 그 날짜의 예약만 상세 API로 받는다.** 이미 받은 날짜는 다시 받지 않는다.
- **화면은 그대로여야 한다.** 날짜마다 그려지는 예약, `+N`의 N, 날짜 안의 순서가 개선 전과 같아야 한다.
- **잘못된 날짜 쿠키는 오늘 날짜로 바꾸지 않고 쿠키 이름이 담긴 오류로 거절한다.** 사용자가 쿠키를 직접 고친 경우뿐이므로 예상과 다른 동작이 일어나지 않게 하는 편이 낫다고 판단했다.

개선 효과의 목표도 측정 전에 정했다. props 500KB 이하, 서버 CPU 70% 절감이다.

## AI가 구현하고, 같은 조건으로 비교했다

구현과 측정은 AI에게 맡겼다. 나는 테스트 결과와 수치를 내 PC에서 확인했다. 핵심은 더보기에서 같은 날짜를 한 번만 받는 부분이다.

```ts
// 개선 코드 (간단히 옮긴 코드)
const detailByDate = new Map<string, Promise<Booking[]>>();

function showMore(date: string) {
  if (!detailByDate.has(date)) {
    const request = api.bookingsByDate(date).catch((error) => {
      detailByDate.delete(date); // 실패하면 비워서 다시 누를 수 있게 한다
      throw error;
    });
    detailByDate.set(date, request);
  }
  return detailByDate.get(date);
}
```

받은 결과가 아니라 요청 `Promise`를 저장하므로, 같은 날짜의 더보기를 동시에 두 번 눌러도 요청은 한 번만 나간다.

테스트는 33개를 더했다. `it.fails` 3개와 같은 기대값을 일반 `it`으로 통과시켰고, 월 예약 8,000·2,000·100·7건에서 개선 전후에 화면에 그려지는 예약이 같은지도 확인했다. 전체 74개가 모두 통과한다.

같은 조건(월 8,000건, 지연 20ms, 힙 한도 1GB, 같은 컴퓨터에서 같은 명령)으로 비교한 결과다.

| 지표 | 당시 방식 | 개선 방식 | 변화 |
|---|---|---|---|
| 요청 수 | 15개 | 15개 | 같음 |
| 응답 합계 | 3,972.9KB | 64.3KB | -98.4% |
| props | 9,886.9KB | 90.4KB | -99.1% (목표 500KB 이하 달성) |
| SSR 1건 서버 CPU | 약 51ms | 약 1.3ms | -97% (목표 70% 절감 달성) |
| 한 프로세스의 처리 한계 | 초당 약 19.7건 | 초당 약 742건 | 약 38배 |
| SSR 응답 시간 (동시 1건) | 236.8ms | 190.1ms | -46.7ms |

동시 요청이 몰릴 때 마지막 응답이 나가는 시간이다.

| 동시 요청 | 당시 방식 | 개선 방식 |
|---|---|---|
| 20건 | 약 1,022ms | 217.9ms |
| 100건 | 약 4,416ms | 250.1ms |
| 600건 | 약 25,286ms | 536.2ms |

더보기의 비용도 쟀다. 예약이 가장 많은 날짜(258건)의 상세 응답이 128.3KB이고, 누른 날짜마다 한 번만 받는다.

## 결과를 어떻게 읽었나

요청 수는 15개 그대로다. 줄어든 것은 요청의 개수가 아니라 **Next 서버가 하던 예약 파싱, 정규화, 직렬화 일**이다. 화면에 그리지 않을 예약을 서버가 받지 않으니 그 비용이 사라졌고, 동시 600건의 마지막 응답이 25초에서 0.5초로 줄었다.

다만 비용이 없어진 것은 아니다. 날짜별로 예약을 세고 앞 4건을 고르는 일은 API 서버로 옮겨 갔고, 이번 측정에는 들어 있지 않다. 이 개선이 전체 시스템에서 얼마나 이득인지는 API 서버의 집계 비용까지 재야 말할 수 있다.

## 느낀 점

- **AI가 한 일**: 기록을 바탕으로 당시 구조를 재현하고, 테스트와 `it.fails`를 만들고, 정한 조건대로 측정하고, 내가 고른 방향대로 구현했다.
- **내가 한 일**: 어떤 상황에서 누가 쓰는지 정하고, 지표와 측정 조건을 정하고, 대형 매장의 동시 요청을 따로 재 달라고 요청하고, 개선 방향과 범위를 정하고, 결과 해석을 확인했다.

메모리가 병목일 것이라는 처음 예상이 틀렸다는 점이 이번에 가장 크게 배운 부분이다. 직관으로 정한 지표 대신 CPU 시간을 항목별로 쪼개서 봤기 때문에 비용이 직렬화와 파싱에 몰려 있다는 것이 보였다. 측정 방식이 틀려서 한 번 고쳤다는 점도 기록해 둔다. 숫자를 얻은 뒤에는 무엇이 그 숫자에 들어 있는지부터 확인해야 한다.

## 한계

- **재현의 범위**: 남겨 둔 기록을 바탕으로 재현했다. 기록에 없는 세부 동작은 당시와 다를 수 있다. 8,000건도 기억에 의한 추정이다.
- **API는 가정**: 요약 API와 상세 API는 실험을 위한 가정이고, 서비스에는 적용하지 못했다. API 서버가 날짜별로 집계하는 비용은 측정하지 않았다.
- **렌더링 미측정**: React 렌더링과 브라우저 렌더링 시간은 재지 않았다. 서버 CPU와 props 크기만 비교했다.
- **측정 환경**: 시간은 내 컴퓨터 기준의 상대 비교이고 서버 사양을 가정한 값이 아니다. 힙 증가는 요청이 끝나는 시점에 잰 하한이다. 가짜 서버는 응답을 소켓에 쓰지 않으므로 느린 클라이언트에 응답을 보내는 동안의 메모리는 반영하지 않는다.
- **운영 장애와의 연결**: CPU가 병목이라는 재현 결과는 2023년 장애의 모양과 맞지만, 장애 원인을 확정하는 근거는 아니다.
- **범위 밖**: 주·일 보기의 조회 개선, 서버 캐시, 공통 요청 6개의 병렬화, 취소된 요청의 작업 중단, 쿠키 속성(`HttpOnly`·`Secure`·`SameSite`)은 다루지 않았다.
