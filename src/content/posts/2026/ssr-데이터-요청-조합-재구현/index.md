AI와 함께 작성한 글입니다.

2022년에 내가 만든 SSR 공통 데이터 요청 조합은 콜백을 하나씩 차례로 실행했다. 실제로 앞 결과가 필요한 것은 토큰 하나뿐이었는데, 서로 관계없는 요청까지 순서대로 기다리게 만든 것이다. 기록을 바탕으로 같은 흐름을 재현하고 동시에 실행할 콜백을 묶음으로 넘기도록 고치자, 요청 수 7개는 그대로인 채 순서대로 기다리는 단계가 7에서 4로 줄었다. 동시에 실행하면서 실패 처리와 결과 병합이 응답 순서에 따라 달라지지 않도록, 묶음이 모두 끝난 뒤 정한 순서로 판단하게 했다. 단계 수는 요청당 지연을 20ms로 같게 준 가짜 API 서버에서 측정한 값이다.

예약 관리 서비스의 웹 페이지는 서버 사이드 렌더링(SSR) 때마다 같은 공통 데이터를 받는다. 토큰을 발급받고, 내 정보와 메뉴, 매장 정보, 매장 목록을 받은 뒤에야 페이지 데이터를 요청한다. 2022년 3월에 내가 이 공통 요청을 콜백으로 나눠 조합하는 재사용 로직을 만들었고, 이후 여러 페이지가 같은 방식으로 SSR 데이터를 준비했다.

이 로직은 콜백을 하나씩 차례로 실행했다. 앞 콜백의 결과를 뒤 콜백에서 쓰는 의존 관계를 표현하려던 것이다. 그런데 실제로 앞 결과가 필요한 것은 토큰 하나뿐이었다. 응답이 느려진다는 것은 알았지만 영향이 크지 않다고 보고 따로 측정하지 않았다.

이 글은 그 흐름을 남아 있는 기록을 바탕으로 프레임워크 없는 함수로 다시 만들고, 실제 의존만 남기고 나머지를 동시에 실행하도록 고친 뒤 같은 조건에서 비교한 기록이다. 회사 코드는 쓰지 않았고, 가짜 API 서버로 구성했다.

## 2022년의 나는 무엇을 만들었나

페이지는 공통 콜백 몇 개와 페이지 콜백을 차례로 넘겨 SSR 함수를 만든다. 각 콜백은 앞까지 합친 결과를 받아 객체를 돌려주고, 돌려준 값은 props 하나로 합쳐진다. 같은 키가 있으면 뒤 콜백의 값이 앞을 덮는다.

예시 페이지 하나의 요청은 7개이고, 모두 하나씩 나간다.

```
토큰 발급 → 내 정보 → 메뉴 → 매장 공통 → 업종 카테고리 → 매장 목록 → 페이지 데이터
```

실패 처리도 이 흐름에 묶여 있다.

- **구독이 만료된 매장**: 매장 공통 정보를 받은 직후 구독 결제 화면으로 영구 리다이렉트하고, 뒤의 요청은 보내지 않는다.
- **그 밖의 오류**: 그때까지 합친 props를 모두 버리고 오류 정보만 담아 상태 200으로 응답한다. 요청이 하나라도 실패하면 화면을 제대로 그릴 수 없다고 보고 일부러 이렇게 만들었다. 화면 안에서 오류를 직접 보여 주려고 Next.js 기본 에러 페이지 대신 200과 오류 정보를 택했다.

## 재현해 보니 보인 것

요청마다 시작·종료 시각을 기록하는 가짜 API 서버를 두고 재현했다. 요청당 지연은 20ms로 모두 같게 주었다.

- **요청 7개가 겹치지 않고 하나씩 나간다.** 콜백을 하나 호출하고 끝날 때까지 기다린 뒤 다음 콜백을 호출하기 때문이다.
- **실제 의존은 셋뿐이다.** 내 정보·메뉴·매장 공통은 발급된 토큰을 헤더에 싣는다. 업종 카테고리는 매장 공통이 준 매장 번호가 필요하고, 구독 만료 여부를 확인한 뒤에 요청한다. 매장 목록은 쿠키만 쓴다. 그런데 내 정보·메뉴·매장 공통·매장 목록이 서로를 기다린다.

토큰 하나만 기다리면 되는 요청이 앞 요청의 '차례'까지 기다리고 있었다.

## 테스트로 먼저 기록했다

고치기 전에 당시 동작과 문제를 테스트로 남겼다. 지켜야 하는 동작은 일반 `it`으로, 기대값이 분명한데 당시 방식이 어기는 사례는 `it.fails`로 썼다. `it.fails`는 기대값이 틀릴 때 통과하므로, 통과한다는 것은 당시 방식이 그 사례에서 틀린다는 뜻이다.

- **일반 테스트 18개**: 요청 순서와 값, 토큰을 쓰는 요청은 토큰 발급이 끝난 뒤에 시작한다, 구독 만료 리다이렉트, 오류 시 props 전체 폐기와 200 응답, 같은 키 병합 규칙.
- **`it.fails` 4개**: '토큰을 받은 뒤 내 정보·메뉴·매장 공통·매장 목록이 겹쳐 실행된다'와, 같은 문제를 요청 쌍으로 본 세 가지.

토큰 의존을 일반 테스트로 둔 이유는 고친 뒤에도 지켜야 하는 조건이기 때문이다. 병렬화하면서 토큰 발급까지 한꺼번에 보내면 이 테스트가 잡아낸다. 오류 시 props를 모두 버리는 동작도 일반 테스트로 고정했다. 병렬화하면서 실패 처리가 실수로 바뀌면 알아챌 수 있게 하려는 것이다.

`it.fails`는 오타로 실패해도 통과한다. 그래서 4개를 일반 `it`으로 바꿔 실행하고, 모두 '요청이 겹치지 않는다'는 의도한 이유로 실패하는지 확인했다.

## 무엇을 재야 하는지 정했다

AI는 순서대로 기다리는 단계 수, SSR 응답 시간, props 동일성을 후보로 냈다. 나는 **단계 수 하나만** 쓰기로 했다.

응답 시간은 가짜 서버에 준 지연 값으로 정해진다. 모든 요청에 20ms를 똑같이 주었으니, 응답 시간이 몇 ms 줄었다고 말하는 것은 내가 정한 가정을 다시 읽는 일이다. 실제 API는 요청마다 지연이 다르다. 단계 수는 지연 값과 관계없이 구조가 바뀌었는지를 보여 준다. props가 그대로인지는 테스트가 이미 확인한다.

단계 수는 이렇게 센다. 요청 B가 요청 A가 끝난 뒤에 시작했으면 B는 A를 기다린 것이다. 이렇게 이어지는 가장 긴 사슬의 요청 수가 단계 수다. 요청이 모두 하나씩 나가면 요청 수와 같고, 동시에 나간 요청은 한 단계로 묶인다.

당시 방식은 전체 7단계, 페이지 데이터 전까지의 공통 단계는 6단계였다. 준비 실행 3회와 측정 20회의 값이 모두 같았다.

## 고치는 방향은 내가 정했다

AI가 개선 후보 두 가지를 정리했다. 하나는 동시에 실행할 콜백을 배열로 묶어 넘기는 방식, 다른 하나는 콜백마다 무엇에 의존하는지 선언하게 하는 방식이다. 나는 **묶음 실행**을 골랐다. 실제 의존이 토큰 하나뿐이라 의존을 선언하게 하는 방식은 이 문제에 비해 과하고, 기존 페이지의 호출 모양을 거의 그대로 둘 수 있기 때문이다.

```ts
// 개선 후 예시 페이지: 배열로 묶은 콜백은 동시에 실행한다
export const getServerSideProps = composeServerSideProps(
  setToken,
  [setMyInfo, setCommonMenu, setShopInfo, setMyShopList],
  setPageData,
);
```

동시에 실행하면 새로 정해야 할 것이 생긴다. 하나씩 실행할 때는 순서가 하나뿐이라 고민할 필요가 없었던 부분이다.

- **묶음 안에서 실패하면 무엇을 돌려주나.** 구독 만료와 메뉴 오류가 함께 나면 먼저 끝난 쪽을 따를 수도 있다. 하지만 그러면 같은 요청이 네트워크 속도에 따라 결제 화면으로 가기도 하고 오류 화면을 보이기도 한다. 그래서 묶음이 모두 끝날 때까지 기다린 뒤, 리다이렉트가 하나라도 있으면 리다이렉트를, 없으면 인자 순서상 첫 오류를 돌려주기로 했다. 구독이 만료된 매장은 다른 요청이 실패해도 결제 화면으로 가야 한다.
- **같은 키를 돌려주면 무엇이 남나.** 끝난 순서대로 덮어쓰면 같은 요청에도 props가 매번 달라질 수 있다. 끝난 순서와 관계없이 인자 순서상 뒤의 값이 이기게 했다. 하나씩 실행하던 당시 방식과 결과가 같아진다.
- **묶음 안의 콜백은 서로의 결과를 받지 않는다.** 묶음이 시작되기 전까지 합친 결과만 받는다. 서로 의존하는 콜백이라면 다른 단계로 나눠야 한다.
- **바꾸지 않은 것**: 오류 시 props를 모두 버리는 동작과 200 응답은 그대로 둔다. 앞의 것은 당시 의도한 설계이고, 뒤의 것은 이번 범위 밖이다.

목표도 구현 전에 정했다. 전체 7 → 4단계, 공통 6 → 3단계다.

## AI가 구현하고, 같은 조건으로 비교했다

구현과 측정은 AI에게 맡겼다. 핵심은 묶음을 실행하는 부분이다.

```ts
// 개선 코드 (간단히 옮긴 코드)
for (const step of steps) {
  const callbacks = Array.isArray(step) ? step : [step];
  const before = result; // 묶음 안의 콜백은 모두 같은 '묶음 전 결과'를 받는다
  const settled = await Promise.allSettled(callbacks.map((cb) => cb(before, context)));

  const failures = settled.filter((r) => r.status === "rejected");
  if (failures.length > 0) throw pickFailure(failures); // 리다이렉트 우선, 없으면 인자 순서상 첫 오류

  for (const r of settled) result = { ...result, ...r.value }; // 끝난 순서가 아니라 인자 순서로 합친다
}
```

`Promise.all`이 아니라 `Promise.allSettled`를 쓴 이유는 위의 실패 규칙 때문이다. `Promise.all`은 가장 먼저 실패한 요청에서 끝나서, 어떤 오류를 돌려줄지가 응답 순서에 달린다.

테스트는 18개를 더했다. 당시 방식의 `it.fails`가 기대하던 '토큰 뒤 네 요청이 겹친다'를 일반 `it`으로 옮겨 통과시켰고, 정상 요청의 props가 당시 방식과 깊은 비교로 같은지, 리다이렉트 우선과 인자 순서 병합이 지켜지는지 확인했다. 당시 방식의 22개를 포함해 40개가 모두 통과한다. 개선 테스트가 실제로 동시 실행을 확인하는지도 보았다. 단계 구조 테스트를 당시 방식의 페이지로 바꿔 돌리면 4개가 실패한다.

같은 조건(요청당 지연 20ms, 준비 3회·측정 20회)으로 비교한 결과다.

| 지표 | 당시 방식 | 개선 방식 |
|---|---|---|
| 전체 단계 수 | 7 | **4** |
| 공통 단계 수 | 6 | **3** |
| (참고) 요청 수 | 7 | 7 |

20회 모두 같은 값이고, 목표를 달성했다.

```
당시: 토큰 → 내 정보 → 메뉴 → 매장 공통 → 업종 카테고리 → 매장 목록 → 페이지 데이터
개선: 토큰 → [내 정보 · 메뉴 · 매장 공통 → 업종 카테고리 · 매장 목록] → 페이지 데이터
```

## 결과를 어떻게 읽었나

요청 수는 7개 그대로다. 줄어든 것은 **서로 관계없는 요청이 서로를 기다리던 시간**이다. SSR에 걸리는 시간은 '모든 요청 지연의 합'에서 '가장 긴 사슬의 지연 합'으로 바뀐다.

남은 4단계는 모두 진짜 의존이다. 매장 공통은 토큰이 있어야 하고, 업종 카테고리는 매장 번호가 있어야 하며, 페이지 데이터는 구독 만료 확인이 끝나야 보낼 수 있다. 만료된 매장이라면 페이지 데이터를 받지 않고 바로 리다이렉트해야 하기 때문이다.

이번 측정에서 총 소요 시간도 함께 출력했다(약 172ms → 약 96ms). 하지만 모든 요청에 같은 지연을 준 가정에서 나온 값이라 개선 폭으로 쓰지 않는다. 실제 서비스에서 얼마나 빨라지는지는 실제 API의 지연 분포를 알아야 말할 수 있다.

## 느낀 점

- **AI가 한 일**: 기록을 바탕으로 당시 구조를 재현하고, 테스트와 `it.fails`를 만들고, 정한 지표대로 측정하고, 내가 고른 방향대로 구현했다.
- **내가 한 일**: 어떤 상황에서 누가 쓰는지 정하고, 오류 시 props를 모두 버리는 것이 당시 의도였는지 확인하고, 지표를 단계 수 하나로 정하고, 개선 방향과 실패 우선순위를 정하고, 결과 해석을 확인했다.

2022년에는 '의존 관계를 표현한다'는 것과 '순서대로 기다린다'는 것을 같은 일로 보았다. 실제 의존은 토큰 하나였는데 순서로 표현하니 모든 요청이 의존하는 것처럼 실행됐다. 그리고 동시에 실행하는 순간, 하나씩 실행할 때는 저절로 정해지던 실패 처리와 결과 병합을 직접 정해야 했다. 동시에 실행하더라도 결과는 실행 시점이 아니라 정해진 순서로 결정되게 해야 한다는 것이 이번에 가장 크게 배운 부분이다.

## 한계

- **재현의 범위**: 남겨 둔 기록을 바탕으로 재현했다. 공통 콜백 5개와 예시 페이지 하나만 만들었고, 웹뷰용 토큰 처리와 개발 환경 분기는 뺐다. 페이지 콜백은 요청 1개로 줄였다. 실제 페이지는 페이지 콜백 안에서도 요청을 여러 묶음으로 보낸다.
- **지연은 가정**: 모든 요청에 20ms를 똑같이 주었다. 실제 응답 시간 단축 폭은 측정하지 않았다.
- **API 서버 부하**: 요청 수는 같지만 동시에 나가는 요청이 늘어난다. API 서버 쪽 영향은 측정하지 않았다.
- **서비스 미적용**: 실험 코드에서만 바꿨고 서비스에는 적용하지 않았다.
- **범위 밖**: 오류를 200으로 응답하는 동작, 실패 시 props를 모두 버리는 동작은 바꾸지 않았다. 매장 목록은 쿠키만 써서 토큰 발급과 동시에 시작할 수도 있지만, 가장 긴 사슬이 바뀌지 않아 단계 수에 영향이 없으므로 묶음에 그대로 두었다.
