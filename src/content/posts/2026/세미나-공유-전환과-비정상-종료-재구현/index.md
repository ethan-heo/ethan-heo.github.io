AI와 함께 작성한 글입니다.

화상 세미나 서비스에서 내가 만든 공유 종류 전환과 비정상 종료 처리를 가짜 메시지 브로커 위에서 다시 만들어 보니, 문서 종료 메시지가 참여자 수만큼 나갔다. 10명 방에서 문서를 다른 문서로 바꾸면 10개, 화면으로 바꾸면 발표자 본인을 뺀 9개였다. 화면 공유는 이전 발표자 본인만 정리하는 조건이 있는데 문서에는 그 조건이 없어서 생긴 차이다. 상태는 맞게 유지됐고 불필요한 메시지가 쌓인 문제였다. 이 밖에 교체 종료 메시지가 아무 일도 하지 않는 동작, 접속 확인 타이머를 정리하지 않는 동작, 퇴장 메시지(will)의 재전달, 같은 퇴장 알림이 두 번 오면 나는 오류를 테스트로 기록했다. 개선은 구현하지 않았고, 서버와 미디어 서버는 가짜라서 서버 동작은 가정이다.

## 들어가며

화상 세미나 서비스에서 발표자는 화면, 문서, 유튜브 영상을 공유한다. 내가 만든 부분은 두 가지다. 하나는 발표자가 공유 종류를 바꿀 때 이전 공유를 정리하고 모든 참여자의 화면을 새 공유로 맞추는 일이고, 다른 하나는 참여자의 브라우저가 갑자기 꺼졌을 때 이를 알아채 다른 참여자의 목록과 공유 화면에서 지우는 일이다. 둘 다 실시간 메시지(MQTT)와 redux-saga 위에서 돌아간다.

이 글은 남아 있는 기록을 바탕으로 이 두 흐름을 가짜 메시지 브로커 위에서 다시 만들고, 테스트로 문제를 기록한 내용이다. 개선은 구현하지 않았다. 문제를 어디서 어떻게 확인했는지, 무엇을 문제로 보지 않았는지를 적었다. 회사 코드는 쓰지 않았고, 유튜브 재생 동기화는 내가 만든 부분이 아니라 뺐다.

## 먼저 알아 둘 용어

- **브로커와 토픽**: MQTT에서는 메시지를 '토픽'(채널 이름)에 발행하고, 그 토픽을 구독한 쪽이 받는다. 메시지를 전달하는 서버가 브로커다.
- **퇴장 메시지(will)**: 접속할 때 브로커에 맡겨 두는 메시지다. 클라이언트가 연결 종료 요청 없이 사라졌다고 브로커가 판단하면 대신 발행한다.
- **retain**: 브로커가 토픽의 마지막 메시지를 보관했다가, 나중에 그 토픽을 구독한 쪽에 바로 전달하는 옵션이다.
- **keepalive**: 클라이언트가 이 간격 안에 패킷을 보내야 한다. 브로커는 간격의 1.5배 동안 아무것도 받지 못하면 연결이 끊겼다고 본다.
- **미디어 서버**: 화면 공유 영상을 중계하는 서버다. 화면 공유가 시작되거나 끝나면 세미나 토픽으로 알림을 보낸다.
- **`put`**: redux-saga에서 액션을 스토어에 실제로 보내는 동작이다. 액션 객체를 만들기만 해서는 상태가 바뀌지 않는다.

## 공유 종류를 바꾸는 흐름

공유 상태는 현재 공유 하나와 지금까지의 공유 이력으로 나뉜다. 종류는 화면, 문서, 유튜브 세 가지다.

- **시작**: 화면은 발표자의 스트림을 미디어 서버에 올리고, 문서와 유튜브는 세미나 토픽에 '시작했다'는 메시지를 보낸다. 시작한 발표자도 자기 상태를 바로 바꾸지 않는다. 자기가 받은 메시지로 상태를 바꾼다. 그래서 모든 참여자의 상태가 같은 메시지에 같은 순서로 반응한다.
- **전환**: 시작 메시지를 받은 참여자는 이전 공유를 기억해 두고, 상태를 새 공유로 바꾼 뒤 이전 공유를 정리한다.
- **정리**: 이전 공유가 화면이면 이전 발표자 본인만 자기 스트림을 지운다. 그러면 미디어 서버가 종료 알림을 보내고, 참여자는 그 알림으로 화면 공유를 비운다. 이전 공유가 문서이면 시작 메시지를 받은 참여자가 모두 문서 종료 메시지를 보낸다.

여기서 화면과 문서의 정리 방식이 다르다. 화면에는 '내가 이전 발표자인가'를 확인하는 조건이 있어서 한 명만 정리하고, 문서에는 그 조건이 없어서 메시지를 받은 모든 참여자가 보낸다.

## 비정상 종료를 알리는 흐름

참여자가 접속할 때 브로커에 '내가 갑자기 사라지면 이 메시지를 대신 보내 달라'는 퇴장 메시지(will)를 맡긴다. 이 메시지는 서버가 듣는 제어 토픽으로 발행된다. 접속 유지 확인 간격(keepalive)은 10초다.

- 브라우저를 닫으면 연결 종료 요청 없이 소켓이 닫혀 브로커가 바로 퇴장 메시지를 보낸다.
- 네트워크가 조용히 끊기면 브로커가 마지막 패킷 뒤 간격의 1.5배, 즉 15초 동안 아무것도 받지 못했을 때 보낸다.
- 정상 종료는 연결 종료 요청을 먼저 보내므로 퇴장 메시지가 나가지 않는다.

퇴장 메시지를 받은 서버가 이를 세미나 토픽의 퇴장 알림으로 중계한다고 가정했다. 서버가 실제로 어떻게 했는지는 남은 기록으로 알 수 없다. 참여자는 퇴장 알림을 받으면 발표자 목록, 화면 공유, 스트림, 참여자 목록 순으로 그 사람을 지운다.

## 다시 만든 방식

한 프로세스에 참여자 N명을 띄우고, 메모리 안에서 동작하는 가짜 브로커와 가짜 미디어 서버, 가짜 세미나 서버를 붙였다. 가짜 브로커는 토픽 구독과 발행, 마지막 메시지 보관(retain), 퇴장 메시지 규칙을 따른다. 시간을 직접 흘려보낼 수 있는 가짜 시계도 넣어서 15초나 30초를 실제로 기다리지 않는다. 화면(React)은 만들지 않고 상태와 메시지 흐름만 재현했다. 공유 종류 전환과 비정상 종료 처리는 같은 메시지를 주고받으므로 실험 하나로 묶었다.

사용 상황은 둘이다. 발표자가 문서를 공유하다가 화면 공유로 바꾸는 경우, 화면을 공유하던 발표자가 브라우저를 강제로 닫는 경우다. 참여자는 기본 3명, 중복 메시지를 셀 때만 10명으로 했다.

## 테스트로 문제를 기록했다

재현한 두 흐름을 테스트로 돌려, 당시 방식이 기대와 다르게 동작하는 사례를 찾아 아래 표에 정리했다. 모두 코드를 읽고 의심한 뒤 가짜 브로커 위에서 실제로 일어나는지 확인한 것이다.

| 문제 | 재현 결과 |
|---|---|
| 문서 종료 메시지가 참여자 수만큼 나간다 | 10명 방에서 문서를 다른 문서로 바꾸면 10개, 화면으로 바꾸면 발표자 본인을 뺀 9개가 나갔다. 화면 공유를 시작한 사람은 이전 공유 정리를 부르지 않기 때문이다. 메시지마다 문서 위에 그린 그림 데이터가 함께 실린다 |
| 교체(replace) 종료 메시지가 아무 일도 하지 않는다 | 종료 메시지의 구분값이 '교체'이면 상태를 바꾸는 액션을 만들기만 하고 `put`으로 보내지 않아, 이력이 그대로 남는다(코드 1) |
| 접속 확인 타이머를 정리하지 않는다 | 접속하면 연결될 때까지 300ms마다 확인하고 30초가 지나면 실패로 끝낸다. 그런데 확인 타이머를 정리하지 않아, 31초째에 연결되자 남은 타이머가 이를 보고 상태를 `using`(사용 중)으로 바꿨다(코드 2) |
| 퇴장 메시지가 마지막 메시지로 보관된다(retain) | 퇴장 메시지는 제어 토픽에 retain으로 발행된다. 서버가 이 토픽을 다시 구독하면(서버 재시작을 흉내 냈다) 이미 나간 사람의 퇴장 메시지를 다시 받는다 |
| 같은 사람의 퇴장 알림이 두 번 오면 오류가 난다 | 위의 재전달처럼 같은 알림이 다시 오면, 두 번째에는 참여자 목록에 그 사람이 없어 `TypeError`가 난다(코드 3). 메시지 처리 반복문이 오류를 잡아 보고만 하므로 다음 메시지는 처리된다. 같은 알림이 실제로 두 번 오는지는 확인하지 못했다 |
| 퇴장한 발표자의 문서·유튜브 공유가 남는다 | 퇴장 처리는 화면 공유만 멈춘다. 문서나 유튜브를 공유하던 사람이 나가면 모든 참여자 화면에 그 공유가 남는다. 의도였는지는 알 수 없다 |
| 화면 재생을 기다리는 동안 온 메시지가 버려진다 | 화면 공유 시작 알림을 처리하는 약 1.3초 동안은 다음 메시지를 받을 곳이 없다. 메시지 채널에 버퍼가 없기 때문이다. 이 사이에 퇴장 알림이 오면 그 참여자의 목록에는 나간 사람이 남는다 |

### 코드로 보는 세 가지

아래 코드는 원리를 보이려고 줄여 쓴 예시다. 실험 코드와 글자까지 같지는 않다.

**코드 1. 교체 종료 메시지**: `updateSharing`은 액션 객체를 돌려줄 뿐이다. `put`으로 보내지 않아서 이력이 바뀌지 않는다.

```ts
function* onDocumentShareFinished(message) {
  if (message.sharingStatus === "replace") {
    updateSharing(/* 이력을 갱신하는 내용 */); // yield put(...)이 없다
  }
}
```

**코드 2. 접속 확인 타이머**: 30초 뒤 실패를 알리지만 `setInterval`은 정리하지 않는다. 그래서 늦게 연결되면 실패 뒤에도 상태가 바뀐다.

```ts
const poll = setInterval(() => {
  if (client.connected) {          // 31초째에 true가 되어도 여기를 지난다
    clearInterval(poll);
    setStatus("using");
  }
}, 300);

setTimeout(() => {
  reportTimeout();                 // 실패를 알리지만 poll은 그대로 돈다
}, 30_000);
```

**코드 3. 같은 사람의 퇴장 알림이 두 번 올 때**: 이미 목록에서 빠진 사람이면 `findUser`가 `null`을 돌려주고, 바로 다음 줄이 `null`의 속성을 읽는다.

```ts
const user = findUser(participants, id); // 두 번째 알림에서는 null
removeFromPresenters(user.type);         // TypeError
```

문서 종료 메시지 중복은 상태를 망가뜨리지는 않았다. 정리하며 보내는 종료 메시지에는 시작할 때의 구분값('새 공유'인지 '교체'인지)이 그대로 실려 있다. 현재 공유를 비우는 값(종료)이 아니므로 받는 쪽에서 무시되거나 코드 1처럼 아무 일도 하지 않는 분기로 빠진다. 그래서 상태 오류가 아니라 불필요한 메시지 트래픽 문제로 적었다. 당시 이 중복을 알고 있었는지는 기억나지 않는다.

두 가지는 문제가 아니라 지켜야 하는 동작으로 확인해 테스트로 남겼다. 하나는 화면에서 문서로 바꿀 때 이전 발표자 본인만 스트림을 지우고, 뒤이은 종료 알림이 새 문서를 지우지 않는다는 점이다. 정리 방식을 바꾸다가 새 문서가 사라지면 이 테스트가 알려 준다. 다른 하나는 화면 공유 중 브라우저의 공유 중지 버튼을 누르면 모두의 공유가 비워진다는 점이다.

## 문제가 아니라고 본 것

코드를 읽을 때 이전 공유 정리에 유튜브 분기가 없어서 '유튜브에서 다른 공유로 바꿀 때 정리 메시지가 안 나가는 문제'로 처음 적었다. 그런데 화면은 현재 공유 종류에 맞는 컴포넌트 하나만 그리므로, 공유가 바뀌면 유튜브 플레이어가 저절로 사라진다. 당시에도 이 전환에서 문제를 겪지 않았다고 기억한다. 정리 메시지가 없다는 것과 정리되지 않는다는 것은 다른 이야기였다. 이 사례는 문제 목록에서 뺐다.

## 고친다면

구현하지 않았고, 방향만 적는다. 문제마다 기대하는 동작을 테스트로 적어 두었으니, 고친 뒤 그 테스트가 통과하는지 보면 된다.

- 문서 종료 메시지는 이전 공유자 한 명만 보낸다.
- 교체 종료 메시지를 받으면 상태를 바꾸는 액션을 `put`으로 실제로 보낸다.
- 접속 확인 타이머는 실패를 보고할 때 함께 정리한다.
- 같은 사람의 퇴장 알림이 다시 와도 목록에 없으면 무시한다. 퇴장 메시지를 마지막 메시지로 보관할지는 서버가 이 토픽을 어떻게 쓰는지 알아야 정할 수 있다.

## 느낀 점

- **AI가 한 일**: 남은 기록을 바탕으로 두 흐름을 가짜 브로커 위에서 재현하고, 테스트를 만들고, 실험을 정리했다.
- **내가 한 일**: 어떤 상황을 기준으로 삼을지 정하고, 유튜브 분기 사례를 문제에서 빼는 데 동의하고, 코드를 읽으며 점검 질문에 답하고, 재생 대기 중 메시지 유실을 문제로 기록하기로 정하고, 직접 데모를 실행해 보았다.

메시지로 맞추는 실시간 상태에서는 '누가 정리하는가'를 정하지 않으면 참여자 수만큼 같은 일을 한다. 상태가 맞더라도 불필요한 메시지가 쌓인다. 화면은 본인 확인 조건이 있어 한 번만 정리했는데 문서는 없어서 열 번 정리했다. 같은 정리 흐름인데 종류마다 처리가 달라진 지점이 문제의 시작이었다.

## 한계

- **서버 동작은 가정**: 서버가 퇴장 메시지를 중계하는 방식과 정상 퇴장을 알리는 방식은 남은 기록으로 알 수 없어 가정했다. 가정이 틀리면 비정상 종료 쪽 결과가 달라질 수 있다.
- **재접속은 다루지 않았다**: 네트워크가 끊겼다 다시 붙는 경우를 당시 어떻게 처리했는지 알 수 없어 재현하지 않았다.
- **화면과 일부 기능 제외**: 화면(React), 문서 변환 진행률, 그림판, 페이지 이동, 유튜브 재생 제어는 만들지 않았다.
- **개선·측정 없음**: 문제를 기록했을 뿐 고치지 않았고, 메시지 트래픽이 실제로 얼마나 늘어나는지는 측정하지 않았다.
- **서비스 미적용**: 실험 코드에서만 다시 만들었다.
- **고칠 방향을 적지 않은 문제**: 퇴장한 발표자의 공유가 남는 동작은 의도였는지 알 수 없고, 재생 대기 중 메시지 유실은 당시 어떻게 보였는지 알 수 없어 '고친다면'에 방향을 적지 않았다.
