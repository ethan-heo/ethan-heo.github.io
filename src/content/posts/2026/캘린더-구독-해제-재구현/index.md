AI와 함께 작성한 글입니다.

예약 관리 화면의 캘린더 구독·해제 흐름을 가짜 캘린더와 가짜 시계 위에서 다시 만들어 보니, 캘린더가 끝내 준비되지 않으면 대기 타이머가 멈추지 않았고, 화면을 다시 열면 해제가 구독한 캘린더와 다른 인스턴스로 갈 수 있었다. 나중에 만든 모듈의 대기 함수는 한도를 8초로 뒀지만 확인 간격 때문에 9초에 실패했고, 성공해도 타이머가 한도까지 남았다. 모두 다시 만들면서 코드를 읽고 찾은 것이고 당시 겪은 문제는 아니다. 개선은 구현하지 않았고, 실제 FullCalendar와 Next.js 환경은 쓰지 않았다.

## 들어가며

예약 관리 화면에는 FullCalendar로 만든 캘린더가 있다. 날짜가 바뀌거나 예약을 옮기면 화면의 여러 곳이 그 이벤트를 받아 자기 일을 한다. 그런데 캘린더 인스턴스는 캘린더 컴포넌트가 마운트된 뒤에야 생긴다. 그래서 이벤트를 받으려면 인스턴스가 생길 때까지 기다린 뒤 구독하고, 화면을 떠나면 해제해야 한다.

내가 만든 부분은 이 대기와 구독·해제 흐름이다. 처음에는 훅 안에서 인스턴스를 모듈 전역 변수로 들고 100ms마다 준비됐는지 확인하는 방식이었고, 나중에 구독을 use case로 정의한 새 모듈과 8초 한도가 있는 대기 함수를 더했다.

이 글은 남아 있는 기록을 바탕으로 두 방식을 가짜 캘린더 위에서 다시 만들고, 테스트로 문제를 기록한 내용이다. 당시 대기가 끝나지 않거나 리스너가 남는 문제를 겪지는 않았다. 아래 문제는 모두 다시 만들면서 코드를 읽고 찾은 것이다. 개선은 구현하지 않았고, 회사 코드는 쓰지 않았다.

## 먼저 알아 둘 용어

- **구독과 해제**: `on(이벤트, 함수)`로 "이 이벤트가 오면 이 함수를 불러 달라"고 등록하고, `off(이벤트, 같은 함수)`로 취소한다. 취소하지 않으면 화면이 사라진 뒤에도 함수가 불린다.
- **effect의 정리 함수**: React에서 `useEffect`가 돌려주는 함수다. 화면이 사라지거나 의존성 값이 바뀌면 React가 부른다. 구독은 effect 안에서 하고 해제는 정리 함수에서 한다.
- **폴링**: 일정 간격으로 "준비됐나?"를 반복해서 확인하는 방식이다. 여기서는 `setInterval`로 구현한다. `setInterval`은 컴포넌트와 연결되어 있지 않아서, 컴포넌트가 사라져도 `clearInterval`을 부르기 전에는 멈추지 않는다.
- **모듈 전역 변수**: 파일 맨 위에 선언해 그 파일을 쓰는 모든 곳이 공유하는 변수다. 값을 비우는 코드가 없으면 한 번 채워진 값이 계속 남는다.
- **클라이언트 이동**: Next.js에서 `next/link`나 `router.push`로 화면을 바꾸는 방식이다. 페이지를 다시 불러오지 않으므로 모듈 변수와 타이머가 이동 뒤에도 살아 있다. 이 서비스의 화면 이동이 이 방식이었다.

## 기존 방식의 흐름

1. 캘린더 컴포넌트가 마운트되면 인스턴스를 모듈 전역 변수에 넣는다.
2. 구독 훅은 effect 안에서 구독 함수를 부른다. 이 함수는 `setInterval`로 100ms마다 변수에 인스턴스가 있는지 확인하다가, 있으면 `on`을 부른다. 첫 확인은 시작 100ms 뒤이므로 인스턴스가 이미 있어도 `on`은 최대 100ms 늦게 실행된다.
3. 구독 함수는 대기가 끝나기를 기다리지 않고 해제 함수를 바로 돌려준다. 해제 함수는 부르는 시점의 변수에 들어 있는 인스턴스에 `off`를 부른다. 변수를 비우는 코드는 없다.

대기에는 제한 시간도 취소 수단도 없다. 구독 방식은 이벤트 종류만 다를 뿐 같은 구조라서, 날짜 변경·예약 드롭·리소스 변경 등 여러 곳이 같은 흐름을 쓴다.

## 새 모듈의 흐름

나중에 만든 모듈은 구독을 use case로 정의했다. 구독 use case는 먼저 "인스턴스가 생길 때까지 기다리는 함수"를 부르고, 끝나면 구독해서 해제 함수를 돌려준다. 대기 함수는 1.5초 간격으로 확인하고, 확인할 때마다 경과 시간을 더해 8초 이상이면 실패로 끝낸다. 인스턴스는 도우미 객체의 필드에 보관하고, 캘린더가 다시 마운트되면 새 인스턴스로 덮어쓴다. 해제 함수는 해제하는 시점의 필드에 `off`를 부른다. 이 구독을 호출하는 곳은 아직 없고, 실제 구독은 모두 기존 방식이 맡고 있었다.

## 다시 만든 방식

가짜 캘린더와 가짜 시계를 만들었다. 가짜 캘린더는 `on`과 `off`를 기록하고 이벤트 종류별 리스너 수를 센다. 가짜 시계는 `setInterval`을 대신하고, 원하는 만큼 시간을 흘려보내며 살아 있는 타이머 수를 센다. 그래서 60초나 9초를 실제로 기다리지 않는다. React의 effect와 정리 함수는 `renderHook`으로 실제로 돌렸다. 화면(Next.js)과 실제 FullCalendar는 쓰지 않았다.

사용 상황은 세 가지다. 화면에 들어와 구독하고 해제하는 일반 흐름, 보기(일·주·월)를 바꿔 effect가 다시 도는 경우, 화면에서 나갔다가 다시 들어와 캘린더가 새로 마운트되는 경우다. 구독은 같은 구조라서 날짜 변경, 리소스 변경, 오늘 판정을 대표로 만들었다.

## 테스트로 문제를 기록했다

다시 만든 코드를 테스트로 돌려, 기대와 다르게 동작하는 사례를 아래 표에 정리했다. 모두 코드를 읽고 의심한 뒤 가짜 캘린더 위에서 실제로 일어나는지 확인한 것이다.

| 문제 | 재현 결과 |
|---|---|
| 캘린더가 끝내 준비되지 않으면 대기가 멈추지 않는다 | 60초가 지나도 100ms 타이머가 1개 살아 있다. 제한 시간도 취소 수단도 없다. 클라이언트 이동에서는 화면을 떠나도 타이머가 멈추지 않는다 |
| 화면을 다시 열 때 구독이 이전 화면의 캘린더에 붙을 수 있다 | 변수를 비우지 않아서, 새 캘린더가 준비되기 전에 대기가 끝나면 `on`이 이전 화면의 캘린더에 붙는다. 새 캘린더에는 리스너가 0개다. 새 캘린더가 100ms보다 늦게 준비되는지는 확인하지 못했다 |
| 리소스 변경 콜백이 한 번 예외를 던지면 이후 변경에 반응하지 않는다 | 다음 대기를 이어 붙이는 연결이 끊기고, 처리되지 않은 Promise 거절이 생긴다. 리스너는 남아 있지만 콜백은 더 불리지 않는다 |
| 새 모듈의 대기 함수는 성공해도 타이머가 남는다 | 조건이 참이 되어 끝나도 1.5초마다 계속 확인하다가 한도 시점인 9초에 사라진다 |
| 새 모듈의 대기 함수는 8초 안이 아니라 9초에 실패한다 | 의도는 8초 안에 실패하는 것이었다. 1.5초 간격으로 확인하면 7.5초에는 8초 미만이고 9초에 처음 8초 이상이 된다 |
| 새 모듈은 다시 마운트된 뒤 해제하면 옛 캘린더에 리스너가 남는다 | 구독은 구독 시점의 인스턴스에, 해제는 해제 시점의 필드에 부른다. 인스턴스가 바뀌면 옛 인스턴스에는 `on`만 남는다. 이 구독은 서비스에서 쓰이지 않아 실제로 일어난 문제가 아니다 |

### 코드로 보는 두 가지

아래 코드는 원리를 보이려고 줄여 쓴 예시다. 실험 코드와 글자까지 같지는 않다.

**코드 1. 구독과 해제**: 대기가 끝난 뒤에 `on`을 부르고, 해제는 그 순간의 변수를 읽어 `off`를 부른다. 변수에는 값을 넣는 곳만 있고 비우는 곳이 없다.

```ts
let calendar; // 모듈 전역. 한 번 채우면 비우지 않는다

function subscribe(event, callback) {
  waitUntilReady(() => calendar.on(event, callback)); // 100ms마다 확인, 취소할 수 없다
  return () => calendar.off(event, callback); // 해제하는 시점의 calendar에 부른다
}
```

**코드 2. 새 모듈의 대기 함수**: `clearInterval`이 한도 분기 안에만 있다. 조건이 참이 되어 `resolve`해도 타이머는 한도까지 돈다.

```ts
const id = setInterval(() => {
  time += 1500;
  if (time >= limit) {
    clearInterval(id);
    reject(new Error("timeout"));
  }
  if (isReady()) resolve(); // 여기서는 clearInterval을 부르지 않는다
}, 1500);
```

### 문제는 아니지만 알아 둘 동작

보기를 바꾸면 의존성 값이 바뀌어 정리 함수가 돌고 새로 구독한다. 새 구독은 대기를 거치므로 첫 확인인 100ms 뒤에 `on`이 실행된다. 그 사이에는 리스너가 0개라서 날짜 변경 이벤트가 와도 콜백이 불리지 않고, 놓친 이벤트가 쌓이거나 다시 전달되지도 않는다. 이 100ms 사이에 이벤트가 오는 일이 실제로 있었는지는 확인하지 못했다. 그래서 문제로 적지 않고 동작으로만 남겼다.

## 고친다면

구현하지 않았고, 방향만 적는다. 문제마다 기대하는 동작을 테스트로 적어 두었으니, 고친 뒤 그 테스트가 통과하는지 보면 된다.

- 대기에는 제한 시간을 두고, 화면을 떠나면 취소할 수 있게 한다.
- 인스턴스를 모듈 전역 변수가 아니라 화면 쪽(Context나 ref)에서 들고, 구독을 건 인스턴스에서 해제한다.
- 콜백이 예외를 던져도 다음 변경에 계속 반응하도록 예외를 잡는다.
- 새 모듈의 대기 함수는 조건이 참이 되면 바로 타이머를 해제하고, 한도는 경과 시간을 기준으로 정확히 8초에 맞춘다.

## 느낀 점

- **AI가 한 일**: 남은 기록을 바탕으로 두 방식을 가짜 캘린더 위에서 다시 만들고, 테스트를 만들고, 결과를 정리했다.
- **내가 한 일**: 재구현 범위(기존 방식과 새 모듈 모두, 구독은 대표만)를 정하고, 코드를 읽으며 점검 질문에 답하고, 화면 이동이 클라이언트 이동이었는지 확인해 문제의 근거를 보강했다. 실제로 일어나기 어려운 경우는 글에서 뺐고, 새 모듈 대기 함수의 의도(8초 안에 실패)를 확인했다.

타이머와 모듈 변수는 React 컴포넌트가 사라져도 남는다. 클라이언트 이동으로 화면을 바꾸는 앱에서는 모듈과 타이머가 계속 살아 있어서, 컴포넌트의 생명주기에 묶이지 않은 상태는 정리해 주는 곳이 없다. 대기를 폴링으로 구현하면 구현은 간단하지만, 멈추는 방법과 누가 멈추는지를 함께 정하지 않으면 그 단순함이 나중에 비용이 된다.

## 한계

- **가짜 캘린더와 jsdom**: 실제 FullCalendar와 Next.js의 라우팅, 서버 렌더링은 쓰지 않았다. 실제 렌더 트리에서 구독 effect와 초기화 effect가 어떤 순서로 도는지도 확인하지 못했다.
- **확인하지 못한 순서**: 새 캘린더가 100ms보다 늦게 준비되는 일이 실제로 있었는지는 알 수 없다. 그래서 이전 캘린더에 구독이 붙는 문제는 당시 문제가 아니라 다시 만들며 찾은 문제다.
- **새 모듈의 구독은 쓰이지 않는다**: 새 모듈 문제는 코드를 읽고 찾은 것이고 서비스에서 일어난 일이 아니다.
- **일부 구독만 재현**: 사용처가 없는 구독과 이벤트·리소스를 바꾸는 나머지 함수는 만들지 않았다. 구독이 렌더링마다 반복되던 문제는 다루지 않았다.
- **개선·측정 없음**: 문제를 기록했을 뿐 고치지 않았고, 대기 타이머나 리스너가 실제로 얼마나 쌓이는지는 측정하지 않았다.
- **서비스 미적용**: 실험 코드에서만 다시 만들었다.
