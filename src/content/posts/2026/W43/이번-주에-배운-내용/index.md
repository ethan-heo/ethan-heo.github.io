AI와 함께 작성한 글입니다.

이번 주에는 서로 다른 세 주제를 공부했다. 선제형 AI에서는 언제 먼저 개입해야 하는지를, TanStack Start에서는 라우트에 필요한 데이터를 언제 준비할지를, CVE-2026-110264에서는 입력 자체와 입력을 처리하는 구현의 위험을 어떻게 구분할지를 살펴봤다. 세 주제는 모두 “무엇을 할 것인가”보다 “어떤 맥락에서, 어느 시점에, 어디까지 판단할 것인가”를 정하는 문제로 이어졌다.

## 선제형 AI는 언제 먼저 말해야 하는가

선제형 AI(Proactive AI)는 사용자가 명령할 때까지 기다리지 않고 상황을 살펴 먼저 도움을 제안하는 AI다. 중요한 것은 먼저 말하는 횟수가 아니다. 사용자가 이미 맡긴 일과 현재 작업의 맥락을 읽고, 놓치면 중요한 일을 적절한 순간에 알려 주는지가 더 중요하다.

내일 중요한 발표가 있는데 자료가 아직 끝나지 않았다면 “지금 초안을 검토할까요?”라고 먼저 제안하는 것이 도움이 될 수 있다. 반대로 사용자가 긴급한 버그를 수정하는 중인데 관련 없는 뉴스나 일정 알림을 보내면, 정확한 정보라도 작업을 방해한다.

놓칠 가능성만으로 알림 여부를 정할 수도 없다. 놓칠 확률이 낮더라도 안전·보안·중요한 마감처럼 영향이 큰 일은 별도로 고려해야 한다. 이번에 정리한 기준은 영향이 매우 큰 일은 확률이 낮아도 알리고, 그보다 낮은 일은 중요도와 놓칠 가능성을 함께 보는 것이다. 이는 원문 연구의 공식 규칙이 아니라 이번 학습에서 내가 정리한 판단이다.

중요한 일이라도 현재 작업과 직접 연결되면 즉시 알리고, 관련성이 낮으면 작업을 끊지 않도록 이후 일정으로 미룰 수 있다. 따라서 선제형 AI의 문제는 알릴지 말지만이 아니라 개입 시점과 강도까지 결정하는 문제다.

## TanStack Start에서 데이터는 언제 준비되어야 하는가

TanStack Start의 route loader는 네트워크를 마법처럼 빠르게 만드는 기능이 아니다. 라우트에 필요한 데이터를 컴포넌트 바깥의 로딩 흐름에 두고, 라우터가 프리로딩·캐시·재검증과 함께 관리하게 만든다.

쉽게 말하면 서버가 첫 화면에 필요한 데이터를 준비해 HTML과 함께 내려주면 브라우저는 의미 있는 화면을 바로 그릴 수 있다. 브라우저가 화면을 먼저 그린 뒤 데이터를 따로 가져오면 요청과 렌더링 단계가 하나 더 생긴다. 대신 브라우저 방식은 필요한 부분만 다시 가져와 전체 화면을 새로고침하지 않고 갱신하기 쉽다.

`useEffect`로 데이터를 가져오면 컴포넌트가 먼저 렌더링된 뒤 요청이 시작된다.

```tsx
function Products() {
  const [products, setProducts] = useState([])

  useEffect(() => {
    fetchProducts().then(setProducts)
  }, [])

  return <ProductList products={products} />
}
```

route loader에서는 라우트가 필요한 데이터를 선언하고 컴포넌트가 그 결과를 사용한다.

```tsx
export const Route = createFileRoute('/products')({
  loader: () => fetchProducts(),
  component: Products,
})

function Products() {
  const products = Route.useLoaderData()
  return <ProductList products={products} />
}
```

초기 요청에서는 loader가 서버에서 실행되어 데이터와 HTML을 준비할 수 있고, 이후 라우트 이동에서는 브라우저에서 실행될 수 있다. 서버만 쓰거나 브라우저만 쓰는 방식이 아니라 라우트 생명주기에 따라 실행 위치가 달라진다.

프리로딩은 클릭 뒤 기다리는 시간을 줄이지만, 실제로 이동하지 않으면 요청과 서버 작업이 낭비된다. 지연이 사라지는 것이 아니라 요청 시점을 클릭보다 앞으로 옮기는 셈이다. 프리로딩한 데이터도 영원히 최신인 것은 아니므로 `staleTime`처럼 일정 시간 동안 캐시를 재사용할 기준과, 그 시간이 지난 뒤 다시 요청할 기준이 필요하다.

모든 데이터를 같은 방식으로 다뤄야 하는 것은 아니다. 장바구니 수량처럼 화면에서 자주 바뀌는 임시 상태는 브라우저에서 관리할 수 있다. 하지만 로그인 후 여러 기기에서 동기화해야 하거나 가격·재고·결제처럼 신뢰가 필요한 순간에는 서버가 최종 기준이 되어야 한다. 브라우저의 장바구니 가격은 사용자가 임의로 바꿀 수 있으므로, 결제 직전에는 서버의 현재 가격을 다시 확인해야 한다. 가격이 바뀌었다면 조용히 바꾸지 말고 사용자에게 알려 결제 판단을 다시 할 수 있게 해야 한다.

따라서 loader가 항상 `useEffect`보다 빠르다고 말할 수는 없다. loader가 느리면 라우트가 준비되는 동안 대기 화면이 필요할 수도 있다. loader의 이점은 네트워크 자체가 아니라 데이터 요청 시점·라우트 렌더링·프리로딩·캐시 재사용을 라우터가 함께 조정해 빈 화면과 늦은 데이터 삽입을 줄이는 데 있다.

이번에 이해한 route loader의 장점은 `useEffect`보다 항상 빠르다는 데 있지 않다. 라우트와 데이터의 관계를 라우터가 알고 있으므로 로딩 순서·프리로딩·캐시·재검증을 한 구조 안에서 다룰 수 있다는 데 있다. 화면에 보여 줄 데이터의 신선도와 결제에 사용할 데이터의 신뢰도도 분리해서 판단해야 한다.

## CVE-2026-110264에서 입력과 구현을 구분하기

CVE-2026-110264의 핵심은 정규식이 명령어라는 데 있지 않다. GitLab CE/EE의 정규식 컴파일 과정에서 정수 오버플로가 발생할 수 있고, 특정 조건에서는 인증되지 않은 사용자의 임의 코드 실행으로 이어질 수 있다는 점이 문제다.

정규식은 문자열이 특정 규칙에 맞는지 검사하는 표현이고, 정규식 컴파일은 이를 빠르게 검사할 수 있는 내부 구조로 바꾸는 과정이다. 정수 오버플로는 저장할 수 있는 범위를 넘어선 계산 결과가 잘못되는 현상이다. 필요한 공간이나 반복 횟수를 잘못 계산하면 단순한 오류에서 더 심각한 실행 흐름 문제까지 이어질 수 있다.

공식 자료로 확인할 수 있는 흐름은 다음 정도다.

```text
특수하게 만든 정규식
→ GitLab의 정규식 컴파일
→ 정수 오버플로 가능성
→ 특정 조건에서 임의 코드 실행
```

다만 공개된 자료만으로 공격자의 정확한 요청, 영향을 받은 내부 메모리 위치, `.org` 파일 렌더링이 반드시 공격 진입점인지 여부까지 확정할 수는 없다. 오버플로가 곧바로 서버 장악을 뜻하는 것도 아니다. 오버플로는 원인이고, 코드 실행은 특정 구현 조건과 실행 흐름이 결합한 결과다.

“인증되지 않았다”는 말도 인증 우회가 일어났다는 뜻으로 단정하면 안 된다. 로그인하지 않은 요청이 도달할 수 있는 처리 경로에 취약점이 있다는 뜻일 수 있다. self-managed GitLab은 운영자가 직접 수정 버전으로 업그레이드해야 하며, 수정 버전은 `18.11.13`, `19.0.10`, `19.1.9`, `19.2.9`, `19.3.6`, `19.4.3`, `19.5.1` 이상이다.
