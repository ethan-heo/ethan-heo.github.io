AI와 함께 작성한 글입니다.

카드 결제 결과 처리 흐름을 가짜 결제 대행사와 가짜 브라우저 위에서 다시 만들어 보니, 결과 화면을 새로고침하면 같은 요청이 다시 들어와 승인 호출이 1회에서 2회가 됐고, 로그인 토큰이 없으면 승인 전에 서버 오류가 났다. 둘 다 다시 만들면서 코드를 읽고 찾은 것이고, 당시 서비스에서 겪은 일은 아니다. 개선은 구현하지 않았고, 서비스 환경을 그대로 만든 것이 아니라 모델이다.

## 들어가며

웹 서비스의 카드 결제는 통상 이런 프로세스로 진행된다. 결제 대행사의 결제창에서 인증을 마치면, 결과를 서비스의 결과 주소로 `POST`로 돌려준다. 결과 주소의 서버 쪽 코드는 그 본문을 읽어 승인 API를 부르고, 성공하면 주문 결과 화면을 보여 준다.

이 글은 내가 개발에 참여한 결제 프로세스를 다시 만들어 본 기록이다. 승인 호출을 클라이언트에서 서버 쪽으로 옮기는 일은 동료와 함께 논의해 정했고, 옮기는 코드는 동료가 작성했다.

남아 있는 기록을 바탕으로 이 흐름을 가짜 결제 대행사와 가짜 브라우저 위에서 다시 만들고, 테스트로 문제를 기록했다. 결과 화면을 새로고침해서 승인이 중복 호출된 일이 당시에 있었는지는 모른다. 아래 문제는 모두 다시 만들면서 코드를 읽고 찾은 것이다. 개선은 구현하지 않았고, 회사 코드는 쓰지 않았다.

## 먼저 알아 둘 용어

- **승인**: 결제창에서 인증을 마친 뒤, 서비스 서버가 결제 대행사에 "이 거래를 확정해 달라"고 요청하는 단계다. 인증만으로는 돈이 움직이지 않고 승인까지 끝나야 결제가 완료된다.
- **`POST` 결과 페이지와 새로고침**: 일반적으로 브라우저는 `POST`로 받은 화면을 새로고침하면, 사용자 확인을 거쳐 같은 요청을 같은 본문으로 다시 보낸다. 서버는 이것이 새로고침인지 새 요청인지 구분하지 못한다.
- **PRG(Post/Redirect/Get)**: `POST`를 처리한 뒤 결과를 `GET` 주소로 리다이렉트해 보여 주는 패턴이다. 새로고침해도 `GET`만 다시 보내므로 `POST`가 반복되지 않는다.
- **멱등성**: 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질이다. 승인 API가 같은 거래에 대해 멱등하면 두 번 불려도 문제가 없다.
- **본문 파서**: 요청 본문(폼 형식이나 JSON)을 읽어 객체로 바꿔 주는 도구다. 형식을 알려 주는 헤더가 맞아야 본문을 읽는다.

## 기존 방식의 흐름

1. 결제 화면이 결제 요청 값을 숨은 form에 채우고, PC에서는 결제창을 띄운다. 모바일에서는 form을 결제 대행사의 결제 페이지로 바로 제출한다.
2. 인증이 끝나면 결과가 서비스의 결과 주소로 `POST`로 돌아온다.
3. 결과 주소의 서버 쪽 코드는 요청이 `POST`이면 본문을 읽는다. 본문이 없으면 승인 없이 빈 결과를 넘기고, 있으면 승인 API를 한 번 부른다.
4. 승인에 성공하면 쿠폰 쿠키를 지우고 결과를 화면에 넘긴다. 실패하면 원인 안내 없이 첫 화면으로 보낸다.
5. 결과 화면은 클라이언트에서만 그리고, 넘겨받은 값을 처음 렌더에서 한 번만 상태로 잡는다.

## 다시 만든 방식

서비스의 환경을 그대로 만든 것이 아니다. 결제 완료 처리 흐름이 어떻게 동작하는지 확인할 수 있을 만큼만, 실제로 쓰는 것과 흉내 낸 것을 나누어 만들었다.

| 구분 | 내용 |
|---|---|
| 그대로 옮긴 것 | 결과 처리의 순서(본문 읽기 → 승인 호출 → 쿠폰 쿠키 정리 → 실패 시 이동), 요청 본문을 읽는 라이브러리와 로그인 토큰을 해석하는 라이브러리(실제 라이브러리를 사용) |
| 흉내 낸 것 | 결제 대행사(인증을 마치고 결과를 돌려주는 동작), 승인 API(호출 횟수와 넘어온 값을 기록하고, 같은 거래도 매번 성공으로 응답), 브라우저(새로고침을 직전 `POST`의 재전송으로 처리), 쿠키 저장소, 요청과 응답 |
| 가정한 것 | 모바일에서 결과가 돌아오는 방식(정해진 주소로 `POST`), 대행사가 돌려주는 값 중 일부 |
| 만들지 않은 것 | 결과 화면의 렌더링(처음 렌더에서 값을 고르는 부분만 옮김), 실제 결제 SDK, 백엔드 |

가짜 승인 API가 같은 거래도 매번 성공으로 응답하게 한 것은, 백엔드가 중복 승인을 막았는지 몰라서 아무것도 가정하지 않기 위해서다.

사용 상황은 결제를 마치고 결과 화면이 뜬 뒤 새로고침하는 것으로 정했다. 성공 조건은 "결제 결과 화면을 새로고침해도 같은 거래의 승인이 다시 호출되지 않는다"이다. 정상 결제와 모바일 결제는 일반 흐름으로 함께 확인했다.

### 어떻게 확인했나

- 다시 만든 코드에는 장면 9개(정상 결제, 새로고침, 모바일, 승인 실패, 토큰 없음 등)를 실행하는 데모를 붙였다. 그중 정상 결제와 새로고침 장면은 내가 직접 실행해, 새로고침 뒤 승인 호출이 1회에서 2회로 늘어나는 것을 확인했다.
- 확인한 동작은 테스트로 고정했다. 기대와 다르게 동작하는 두 가지(새로고침 재승인, 토큰 누락)는 '현재는 기대와 다르다'는 표시를 달아 기록했다.
- 그 두 테스트는 AI가 표시를 뗀 복사본으로 돌려, 의도한 이유로 실제로 실패하는지도 따로 확인했다.

## 테스트로 문제를 기록했다

| 문제 | 재현 결과 |
|---|---|
| 결과 화면을 새로고침하면 같은 거래의 승인이 다시 호출된다 | 정상 결제에서 승인은 1회인데, 같은 본문이 다시 들어오면 승인이 2회가 되고 같은 주문 번호로 결과 화면이 그려진다. 이미 처리한 거래인지 확인하는 곳도, 결과를 `GET`으로 넘기는 리다이렉트도 없다 |
| 로그인 토큰이 없으면 서버 오류가 난다 | 토큰을 해석한 결과가 비어 있는데 바로 값을 꺼내려 해서 `TypeError`가 난다. 이 단계가 오류 처리 밖에 있어 승인 호출 전에 서버 오류로 끝난다 |

### 코드로 보는 두 가지

아래 코드는 원리를 보이려고 줄여 쓴 예시다. 실험 코드와 글자까지 같지는 않다.

**코드 1. 결과 처리**: 본문이 있으면 승인을 부른다. 이미 처리한 거래인지 확인하는 줄이 없다.

```ts
function handleResult(req, cookies) {
  const body = req.method === "POST" ? parseBody(req) : undefined;
  if (!body) return { props: { approval: null } };

  const approval = approve({ ...pick(body), ...fromCookies(cookies) }); // 같은 본문이 오면 또 부른다
  return { props: { approval } };
}
```

**코드 2. 토큰 해석**: 해석 결과가 비어 있어도 바로 구조 분해한다.

```ts
const decoded = decode(token); // 토큰이 없으면 null
const { memberId } = decoded; // null이면 TypeError. 오류 처리 밖이다
```

### 문제는 아니지만 알아 둘 현재 동작

다음은 기대하는 동작을 정할 근거가 없어서 문제로 단정하지 않고, 다시 만든 코드의 동작만 기록했다.

- **승인 실패**: 원인 안내 없이 첫 화면으로 보내고, 쿠폰 쿠키는 지우지 않는다. 안내를 기획에서 정했는지는 모른다.
- **금액 대조 없음**: 프론트엔드는 돌아온 금액을 숫자로 바꿔 승인에 넘길 뿐 주문 금액과 비교하지 않는다. 서명은 승인 때 함께 넘어가므로, 검증은 백엔드가 하는 것으로 보이지만 확인하지 못했다.
- **빈 본문**: 폼 형식인데 본문이 비어 있는 `POST`도 본문 파서가 빈 객체로 만들어 승인 API를 부른다. 이때 금액은 숫자가 아닌 값이 된다.
- **알 수 없는 형식과 `GET` 직접 접속**: 본문을 읽지 않아 승인 없이 빈 주문 화면이 그려진다. 오류는 나지 않는다.

## 고친다면

구현하지 않았고, 방향만 적는다. 새로고침과 토큰 누락에 대해 기대하는 동작을 테스트로 적어 두었으니, 고친 뒤 그 테스트가 통과하는지 보면 된다.

- 승인을 처리한 뒤 결과를 `GET` 주소로 리다이렉트해(PRG) 새로고침이 승인을 다시 부르지 않게 한다.
- 승인 요청에 거래 식별자를 기준으로 한 중복 방지를 두거나, 백엔드가 같은 거래를 한 번만 승인하는지(멱등한지) 확인한다.
- 토큰이 없는 요청은 서버 오류가 아니라 로그인 안내 같은 처리로 보낸다.
- 승인 실패 안내와 금액 대조는 기획과 백엔드 책임을 확인한 뒤 정한다.

## 느낀 점

- **AI가 한 일**: 남은 기록을 바탕으로 결제 흐름을 가짜 환경 위에서 다시 만들고, 테스트를 만들고, 결과를 정리했다.
- **내가 한 일**: 재구현 범위(결과 처리 중심, 결제창은 가짜 대행사 위에서 최소로)와 사용 상황을 정하고, 코드를 읽으며 점검 질문에 답했다. 데모의 "승인 1회에서 2회"가 가짜 브라우저를 쓴 모델의 결과이지 실제 서비스의 중복 승인 근거가 아님을 구분했고, 승인 실패 안내와 금액 대조는 문제로 단정하지 않기로 정했다.

`POST`로 그린 화면은 새로고침만으로도 같은 요청이 다시 나간다. 결제처럼 한 번만 일어나야 하는 일은, 화면이 아니라 요청을 처리하는 쪽에서 이미 처리했는지 알 수 있어야 한다. 이 코드는 그 확인이 어디에도 보이지 않았고, 백엔드가 막았는지는 내가 알지 못한다.

## 한계

- **서비스 환경과 다르다**: 서비스 환경을 그대로 만든 것이 아니라 가짜 결제 대행사와 가짜 브라우저를 쓴 모델이다. 실제 대행사가 모바일에서 결과를 어떤 방식으로 돌려주는지, 실제 브라우저가 새로고침 때 같은 요청을 다시 보내는지는 이 서비스의 환경에서 직접 확인하지 못했다.
- **운영 동작 미확인**: 백엔드가 중복 승인이나 금액 불일치를 막았는지 알지 못한다. 그래서 이 글의 "승인 2회"는 다시 만든 모델의 결과이고, 실제 서비스에서 중복 승인이 있었다는 근거가 아니다.
- **화면 범위**: 결과 화면의 렌더링은 만들지 않고, 처음 렌더에서 값을 고르는 부분만 옮겼다.
- **개선·측정 없음**: 문제를 기록했을 뿐 고치지 않았고, 수치를 측정하지 않았다.
- **서비스 미적용**: 실험 코드에서만 다시 만들었다.
