AI와 함께 작성한 글입니다.

소프트웨어에서 모듈은 화면, 함수, 저장소, 서버처럼 역할을 나눈 코드 단위다. 모듈을 나눈 구조에서는 코드를 독립적으로 바꾸기 쉽다. 모듈 사이의 약속은 여전히 필요하다. 화면은 서버가 어떤 상태를 받는지 알아야 하고, 함수는 인수의 의미를 알아야 한다. 문제는 이 지식이 얼마나 크고 명확한 형태로 공유되는가다.

공생성(connascence)은 두 모듈이 얼마나 가까운지가 아니라, 한쪽을 바꿀 때 다른 쪽의 지식까지 함께 바꿔야 하는지를 보여 주는 기준이다. 이름을 맞추는 정도부터 같은 인스턴스를 공유하는 정도까지 아홉 수준으로 나뉘며, 뒤로 갈수록 공유하는 지식이 많고 인터페이스는 덜 명시적이다.

아래 예시는 실제 서비스 코드를 옮긴 것이 아니다. 상담원 화면과 상태 변경 API가 있다고 가정한 TypeScript 실습에서, 화면과 모듈 사이의 약속이 어떻게 드러나는지 확인한 내용이다.

이번에 실습하며 가장 중요하다고 느낀 질문은 이것이었다.

> 이 경계를 넘으려면 두 모듈이 무엇을 알고 있어야 하는가?

이 질문을 먼저 던지면 숫자 하나의 의미, 배열 원소의 순서, 실행 타이밍, 같은 객체를 공유하는 문제를 한 기준으로 비교할 수 있다. 독자는 공생성의 이름을 모두 외우지 않아도, 변경할 때 함께 확인해야 하는 범위를 찾을 수 있다.

## 공생성은 공유하는 지식의 종류로 판별한다

정적 공생성은 코드를 읽어 확인할 수 있는 관계다. 이름, 유형, 의미, 알고리즘, 위치 공생성이 여기에 속한다. 동적 공생성은 실행 중에 드러난다. 실행 순서, 시간 간격, 값의 동시 변경, 동일한 인스턴스 공유가 여기에 속한다.

낮은 수준이 무조건 좋은 것은 아니다. 중요한 것은 요구사항에 필요한 지식을 얼마나 작고 명시적인 계약으로 만들었는지다. 예를 들어 두 모듈이 `7`이라는 숫자를 상태 코드로 해석한다면 두 모듈 모두 그 숫자의 뜻을 알아야 한다. 이런 관계를 의미 공생성이라고 한다. `enum`이나 명시적인 타입으로 바꾸면 이 지식을 이름과 유형의 계약으로 옮길 수 있다.

반면 타이밍이나 값의 동시 변경처럼 요구사항 자체가 만드는 관계는 단순한 타입 변경만으로 없앨 수 없다. 높은 수준의 공생성은 억지로 낮추기보다, 두 모듈을 가까이 두거나 변경 경계를 다시 나눌 신호로 보는 편이 맞다.

## 숫자의 의미를 한 곳에 가두기

상담원 화면에서 티켓을 다시 연다고 가정해 보자. 실습에서는 화면이 상태를 숫자로 직접 다루지 않고 `reopened`라는 이름을 넘기도록 바꿨다. 숫자 코드와 이름의 대응은 `TICKET_STATUS_MAP` 한 곳에만 남겼다.

```ts
const TICKET_STATUS_MAP = {
  reopened: 7,
} as const;

function reopenTicket() {
  return updateTicketStatus(TICKET_STATUS_MAP.reopened);
}
```

화면은 `7`의 의미를 알 필요가 없고, 타입과 이름으로 어떤 상태를 요청하는지 드러난다.

다만 의미 공생성이 사라졌다고 말하면 정확하지 않다. 백엔드 계약이 여전히 숫자이므로, 클라이언트와 백엔드 사이에는 `7`이 무엇을 뜻하는지에 대한 합의가 남아 있다. 바뀐 것은 그 지식을 여러 화면에 퍼뜨리지 않고 어댑터 한 곳에 모았다는 점이다.

문자열을 내려준다고 자동으로 공생성 수준이 낮아지는 것도 아니다. 타입 없이 문자열 리터럴의 뜻만 양쪽이 약속한다면 여전히 의미 공생성이다. 양쪽이 같은 열거형이나 유니온을 계약으로 공유할 때 유형 공생성으로 볼 수 있다.

## 배열 순서는 이름으로 바꿀 수 있다

위치 공생성은 값의 위치나 순서에 의미가 숨어 있는 경우다. 배열의 첫 번째 원소가 발신자이고 두 번째 원소가 수신자라는 합의가 대표적이다. 호출부만 보면 두 문자열이 각각 무엇인지 알기 어렵고, 순서를 바꿔도 오류를 바로 드러내기 어렵다.

실습에서는 배열과 튜플로 주고받던 입력·결과를 이름이 있는 구조로 바꿨다.

```ts
type ReplyRequest = {
  from: string;
  to: string;
  message: string;
};

function sendReply(request: ReplyRequest) {
  return {
    sender: request.from,
    receiver: request.to,
  };
}
```

함수 경계 밖에서는 `from`, `to`, `message`라는 이름으로 계약이 드러났다. 함수 안에서 `Object.entries`가 임시 튜플을 만들더라도 그 튜플이 함수 경계를 넘지 않으면 위치 공생성은 내부 구현에 갇힌다.

여기서 인수를 이름 붙인 구조로 바꿨다고 해서 모든 공생성이 사라지는 것은 아니다. 여러 문자열 인수를 그대로 받으면서 호출 순서에 의미가 남아 있다면 위치 공생성은 그대로다. 이름을 붙이는 일의 효과는 실제 계약의 경계까지 순서 의존성을 밀어내는 데서 나온다.

## 동적 공생성은 타입만 보고 찾을 수 없다

동적 공생성은 실행해야 드러나는 관계다. 데이터베이스 연결은 열기, 트랜잭션 시작, 쿼리, 커밋 또는 롤백, 닫기의 순서를 지켜야 한다. 두 시계 조회 사이에 시간이 흐르면 시와 분이 서로 다른 순간을 가리키는 것처럼, 호출 사이의 시간 간격도 계약이 될 수 있다.

값 공생성은 여러 값이 동시에 바뀌어야 유효한 상태가 유지되는 경우다. 고객의 본인 확인 상태를 나타내는 `isVerified`가 꺼지면 우선 배송 설정인 `priorityShippingEnabled`도 꺼져야 한다고 가정해 보자. 두 값은 서로 독립적인 것처럼 보여도 함께 관리해야 한다. 동일 공생성은 더 강하다. 여러 모듈이 정확히 같은 연결 풀이나 같은 상태 객체를 참조해야 하는 경우다.

“같은 데이터베이스를 사용한다”는 사실만으로 동일 공생성이라고 할 수 없다. 같은 데이터 세트를 즉시 관찰하고 변경 결과가 곧바로 공유된다는 가정까지 있어야 한다. 메시지로 통신하고 일관성을 별도로 보장하지 않는 구조라면 같은 데이터베이스라는 이유만으로 동일 공생성이 되지는 않는다.

## 공생성 수준은 겹칠 수 있다

하나의 연결에는 여러 종류의 공생성이 함께 있을 수 있다. 결제 함수가 다음을 동시에 받는다고 하자.

- 이름과 유형이 있는 인수
- 숫자로 된 거래 유형
- 암호화 알고리즘에 대한 합의
- 순서가 정해진 튜플 반환값

이 연결을 하나의 수준으로 분류해야 한다면 가장 높은 수준인 위치 공생성을 선택한다. 이는 다른 관계가 없다는 뜻이 아니라, 변경 위험이 가장 큰 지식을 우선해서 드러내는 분류 규칙이다.

실습 ex05에서는 아홉 수준을 순서대로 놓고, 여러 신호가 겹칠 때 가장 높은 수준으로 분류하는 규칙을 적용했다. 모듈 결합 유형과의 대응표도 함께 확인했다. 여러 관계가 한 연결에 겹칠 수 있다는 점과, 그중 변경 위험이 큰 지식을 우선해 분류한다는 점을 확인한 실습이다.

## 코드 리뷰에서 다시 사용할 질문

공생성을 찾을 때는 용어를 먼저 외우기보다 다음 질문으로 경계를 읽어 보려고 한다.

1. 이 값의 의미를 양쪽이 숫자나 문자열로 따로 알고 있는가?
2. 데이터의 순서나 실행 순서가 이름 없는 약속으로 남아 있는가?
3. 호출 사이의 시간이나 여러 값의 동시 변경을 가정하는가?
4. 두 모듈이 정확히 같은 객체나 상태를 공유해야 하는가?

그다음에야 그 지식을 타입, 이름 있는 인수, 명시적인 인터페이스로 옮길 수 있는지 본다. 옮길 수 없는 타이밍, 알고리즘, 실행, 값, 동일 공생성은 제거 대상이 아니다. 두 모듈을 가까이 둘지 판단하게 하는 설계 신호다.

공생성은 결합을 없애는 방법이 아니다. 경계를 넘는 지식을 숨기지 않고 이름 붙여 드러내는 방법에 가깝다. 다음 코드 리뷰에서도 함수 호출의 개수보다, 변경 하나가 어떤 모듈의 어떤 지식까지 함께 흔드는지부터 확인하려고 한다.
